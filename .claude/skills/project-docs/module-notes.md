# 模組說明（`module-notes.md`）的格式與寫作標準

專案地圖每個模組的一句白話說明，存在 `.claude/taskmaster-data/module-notes.md`（進 git）。
本檔是格式與寫作標準的唯一來源；寫的人固定是 `documentation-specialist`（ADR-2026-11-05-002）。

**說明層由使用者同意才寫**：程式碼片段會經 Claude Code 送到 Anthropic。`/task-status` 每次都先問，
永遠不自動執行；`project.json` 設 `"overview": {"notes": "off"}` 可整個關掉（地圖照畫，只是沒有說明）。

## 格式

````markdown
---
based_on: a1b2c3d          # 寫說明時的 HEAD（git rev-parse --short HEAD）
generated: 2026-11-05
---
| id | 名稱 | 分組 | 說明 | 依據 |
|---|---|---|---|---|
| auth | 登入與權限 | 後端 | 用公司目錄服務驗證帳號，簽發登入憑證，並檢查每個 API 的角色 | `src/auth/ldap.py` |
````

| 欄 | 寫什麼 | 規則 |
|---|---|---|
| `id` | 地圖上的模組 id | 必須是地圖現有的模組（`overview.sh --notes-todo` 的第 1 欄） |
| 名稱 | 給人看的模組名 | ≤ 12 字（以字元計，全形半形都算 1）。可空：空的就用目錄名。架構文件 5.5 有這個模組時以 5.5 為準 |
| 分組 | 地圖上的分欄（例：前端、後端、排程） | 可空：空的就用掃描出的分組。5.5 有這個模組時以容器圖為準 |
| 說明 | 它替使用者或業務做什麼 | 1–60 字 |
| 依據 | 你讀過、支持這句說明的檔 | 至少一個；每個都要存在、而且在該模組的路徑內。多個用 `、` 分隔，每個包反引號 |

- 只寫一張表，表頭五欄都要有（順序不拘）
- `based_on` 填寫完當下的 HEAD。之後改過某個模組的檔，地圖就把那個模組的說明標成「可能過期」；
  `based_on` 不是有效的 commit 時，全部說明都標成可能過期
- 只更新過期的模組時，`based_on` 照樣改成當下的 HEAD——沒改到的列也一起視為「在這個版本確認過」，
  所以只在你**確實看過**沒改到的列仍然正確時才這樣做；沒把握就把那幾列也重寫

## 寫作標準

**寫它替使用者或業務做什麼，不寫資料夾裡有哪些檔。**

| ✅ 這樣寫 | ❌ 不要這樣寫 | 為什麼 |
|---|---|---|
| 把每日報表匯成 CSV，凌晨排程寄給主管 | 包含 export.py 與 schedule.py | 檔名讀者自己看得到，說明要講用途 |
| 查詢條件存成書籤，下次登入直接套用 | 提供強大且完整的查詢功能 | 空洞詞（強大、完整、一站式、無縫）誰都能套 |
| 呼叫後端報表 API，失敗時重試一次 | 前端的 API 層 | 只是把目錄名換成中文 |
| 用公司目錄服務驗證帳號，簽發登入憑證 | 用 10.1.2.3 的 LDAP 驗證 | 不准寫主機與 IP（見下） |

空洞詞的判準同 `.claude/skills/ui-style-compliance/anti-ai.md` 的「文案與事實」：換到別的專案也成立的句子就是沒寫。

### 絕不寫（金融客戶，寫進去就進了 git）

- 主機名、IP、連線字串（`Server=`、`Data Source=`）、網址裡的帳密
- 帳號、密碼（含 `password`、`pwd=` 字樣）、金鑰
- 客戶名稱、人名、Email

要提到外部系統時寫它的**角色**：「公司目錄服務」不寫主機名、「主要資料庫」不寫連線字串。

## 讀多少

每個模組**最多讀 3 個代表檔、每個最多 200 行**：路由檔、進入點、被引用最多的檔。
`bash .claude/scripts/overview.sh --notes-todo` 已經挑好了（第 3 欄），照它讀，不要整個目錄讀過一遍。
一個模組約 3–6k 輸入 token；30 個模組約 100–180k，之後只重寫過期的。

讀了 3 個檔還說不出它做什麼 → 說明寫你確定的部分，在回報裡列出這個模組，不要猜。

## 機器會檢查什麼

寫入 `module-notes.md` 的當下，`post-write.sh` 會跑 `overview.sh --check-notes`，有違規就注入對話：

- 表頭缺欄
- `id` 不在地圖上
- 名稱超過 12 字、說明是空的或超過 60 字
- 「依據」沒寫、檔案不存在、不在該模組的路徑內
- 名稱、分組、說明含 IP、`Server=`、`Data Source=`、`password`、`pwd=`、網址帳密、Email（不分大小寫）

違規的那一列在地圖上當成沒有說明。**修到沒有注入為止**。機器只驗得出格式，驗不出內容對不對——
內容由寫作標準與使用者抽查（`依據` 欄就是給人抽查用的）把關。

## 範例

以 `make-fixture.sh messy-fullstack` 的查詢系統為例（只用通用詞彙）：

````markdown
---
based_on: 3f9c2e1
generated: 2026-11-06
---
| id | 名稱 | 分組 | 說明 | 依據 |
|---|---|---|---|---|
| backend-api | 後端 API | 後端 | 提供使用者、報表與登入的 REST 介面，每支都先確認登入身分 | `backend/app/api/reports.py`、`backend/app/api/deps.py` |
| services | 查詢服務 | 後端 | 依登入者查使用者與報表資料，報表查詢會先載入使用者 | `backend/app/services/report_service.py` |
| pages | 頁面 | 前端 | 登入、儀表板與報表列表三個畫面 | `frontend/src/pages/Dashboard.tsx` |
````
