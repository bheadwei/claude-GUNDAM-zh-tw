# 程式碼審查與重構指南

> **版本:** v3.0 | **更新:** 2026-07-24

---

## 1. 審查前檢查（提交者）

- [ ] 程式碼可編譯/建置無錯誤
- [ ] 所有測試通過（含新增測試）
- [ ] Linter / Formatter 已執行（Ruff/ESLint/Prettier）
- [ ] 符合專案 `.claude/rules/` 中的編碼規範
- [ ] 已完成自我審查（逐行看過 diff）
- [ ] PR 描述清楚說明「為什麼改」而非「改了什麼」
- [ ] 若使用 AI 產生程式碼，已標註 `[AI-assisted]` 並完成人工複核（見第 7 節）

---

## 2. 審查重點清單（審查者）

### 正確性
- [ ] 邏輯是否正確？邊界條件是否處理？
- [ ] 錯誤路徑是否有適當處理？（不靜默吞噬）
- [ ] 並發安全嗎？（共享狀態、race condition）
- [ ] 資料驗證在系統邊界完成？

### 設計
- [ ] 符合架構分層？（domain 不依賴 infrastructure）
- [ ] 函式 < 50 行、類別 < 200 行？
- [ ] 有沒有不必要的抽象？（三次以上重複才抽取）
- [ ] 命名是否清晰表達意圖？

### 安全（每次都要看）
- [ ] 無硬編碼秘密（API key、密碼）
- [ ] 使用者輸入已驗證/清理
- [ ] SQL 使用參數化查詢
- [ ] 敏感資料不出現在 log 中

### 效能（有疑慮時看）
- [ ] 無 N+1 查詢
- [ ] 大列表有分頁
- [ ] 昂貴操作有快取策略
- [ ] 無不必要的同步阻塞

### 測試
- [ ] 新程式碼有對應測試
- [ ] 測試覆蓋正常路徑 + 邊界 + 錯誤路徑
- [ ] 測試是否脆弱？（不依賴時序、外部狀態）

## 3. Conventional Comments（審查留言標籤）

每則審查留言以標籤開頭，讓意圖與嚴重性一眼可辨；`(blocking)` / `(non-blocking)` 可疊加於任一標籤：

| 標籤 | 意圖 | 是否阻擋合併 | 範例 |
| :--- | :--- | :--- | :--- |
| **praise:** | 肯定良好做法 | 否 | `praise: 這裡的早期返回讓邏輯清楚很多` |
| **nitpick:** | 微小、非必要的偏好 | 否 | `nitpick: 這個變數可以再短一點` |
| **suggestion:** | 具體改善建議 | 否（除非加 blocking） | `suggestion: 考慮改用 Map 避免 O(n²)` |
| **issue:** | 需要處理的問題 | 視嚴重度 | `issue: 這裡沒有處理 null 的情況` |
| **question:** | 釐清意圖，非隱藏批評 | 否 | `question: 這裡為何選擇同步而非非同步？` |
| **blocking:** | 明確標註「必須解決才能合併」 | 是 | `issue (blocking): SQL 未參數化` |

留言格式：`<標籤>[ (blocking)]: <內容>`。審查者應優先用 `suggestion`/`question` 保持協作語氣，僅在確有阻擋必要時才加 `(blocking)`。

## 4. 審查嚴重等級

| 等級 | 定義 | 範例 | 是否阻擋合併 |
| :--- | :--- | :--- | :--- |
| **Blocker** | 安全漏洞或資料遺失風險 | SQL injection、未加密密碼 | 必須修復 |
| **Major** | 明確的 bug 或設計缺陷 | Race condition、錯誤的商業邏輯 | 必須修復 |
| **Minor** | 改善項目，不影響功能 | 命名不佳、可讀性差 | 建議修復 |
| **Nit** | 個人偏好 | 空行數量、import 順序 | 不阻擋 |

## 5. 審查 SLA（服務水準約定）

| PR 類型 | 首次回應時間 | 完整審查時間 | 說明 |
| :--- | :--- | :--- | :--- |
| **Hotfix / 生產事故** | 30 分鐘內 | 2 小時內 | 需指定審查者並同步通知 |
| **一般功能 PR** | 1 個工作日內 | 2 個工作日內 | 逾時需在 PR 留言告知預估時間 |
| **小型 PR（< 100 行）** | 半個工作日內 | 1 個工作日內 | 拆小 PR 有助於加速審查 |
| **文檔 / 設定變更** | 1 個工作日內 | 1 個工作日內 | 可降低審查強度但不可跳過 |

- [ ] 逾時未回應 → 提交者可在 team channel `@` 提醒
- [ ] 連續逾時 → 於團隊回顧檢討審查人力分配

## 6. 重構識別 — Code Smells

| Smell | 症狀 | 重構手法 |
| :--- | :--- | :--- |
| **Long Method** | 函式 > 50 行 | Extract Method |
| **Large Class** | 類別 > 200 行或 > 5 個職責 | Extract Class |
| **Long Parameter List** | 參數 > 4 個 | Introduce Parameter Object |
| **Duplicated Code** | 相同邏輯出現 3+ 次 | Extract Method / Module |
| **Feature Envy** | 方法大量存取另一個類別的資料 | Move Method |
| **Shotgun Surgery** | 一個改動需要改 5+ 個檔案 | 合併到同一模組 |
| **Primitive Obsession** | 到處用 string/int 表達業務概念 | Introduce Value Object |

## 7. AI 輔助審查的人工把關原則

AI（含 Claude Code、Copilot 等）可加速審查，但**最終判斷必須由人類負責**：

- [ ] AI 產出的審查意見視為「草稿」，人類審查者需逐條確認後才能留言
- [ ] `Blocker` / `Major` 等級的判定**禁止**完全交由 AI 自動核准或自動阻擋，需人工複核
- [ ] AI 若標註「無問題」不可作為唯一核准依據；仍需至少 1 位人類審查者過目
- [ ] AI 產生的程式碼提交時標註 `[AI-assisted]`，審查時對其正確性/安全性採**更高標準**而非更低
- [ ] 記錄 AI 誤判案例（false positive/negative），回饋改善 prompt 或審查規則

## 9. 合併流程

### 合併前
- [ ] CI 全綠（build + test + lint + security scan）
- [ ] 至少 1 位同儕 Approve（人類，非 AI）
- [ ] Blocker / Major 全部解決
- [ ] Branch 已 rebase 到最新 main

### 合併後
- [ ] 部署到 Staging 驗證
- [ ] 監控 15 分鐘無異常（error rate、latency）
- [ ] 關閉相關 Issue

## 10. 審查成效指標 — Rework Rate

採 DORA 的 **Rework Rate**（合併後短期內又被修改/回退的變更比例）作為審查品質的落後指標，與四項核心 DORA 指標並列追蹤：

| 指標 | 定義 | 目標 | 資料來源 |
| :--- | :--- | :--- | :--- |
| **Rework Rate** | 合併後 [14] 天內被修復/回退的 PR 佔比 | < [X]% | Git 歷史 + Issue 連結 |
| **首次回應達成率** | 符合第 5 節 SLA 的 PR 比例 | ≥ 90% | PR 系統時間戳 |
| **平均審查輪數** | 每個 PR 平均來回修改次數 | 監控趨勢，非硬指標 | PR 系統 |

- [ ] Rework Rate 持續偏高 → 檢討審查深度是否不足，而非單純加快審查速度
- [ ] 每季回顧一次，與團隊 DORA 儀表板一併呈現
