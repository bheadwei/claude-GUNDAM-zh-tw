# 專案簡報與 PRD 範本

> 一個檔兩個範本：上半是 `docs/00_brief.md`（為什麼做、範圍上限），下半是 `docs/prd.md`（系統該有什麼行為）。
> 兩份分開存檔，各自更新：brief 在方向改變時改；PRD 由 `/verify` 依 plan 的情境變更套回，不手寫進度。
>
> **唯一來源**：`/task-init`、`/docs-init` 都指向這裡，不各自內嵌骨架。

---

# 上半：`docs/00_brief.md`

```markdown
# 專案簡報 — [專案名稱]

> 這份是「我理解到的需求」，經使用者確認過；是 PRD 的輸入。

## 一句話
[做什麼、給誰用、預期效果]

## 要解決的問題
[核心問題；能量化就量化]

## 誰在用
[使用者／角色。沒問到就寫「未釐清」，不要編]

## 核心功能
- [功能 1]
- [功能 2]

## 明確不做（non-goals）
- [排除項 1] — [為什麼不做]

## 成功長什麼樣
[量化優先]

## 最大的未知與風險
| 風險 | 為什麼擔心 | 目前的想法 |
|---|---|---|

## 技術約束
[語言、框架、部署環境、特殊限制]

## 已否決的方案
[替代方案與否決理由；沒有就寫「無」]

## 仍未釐清
[問了但使用者說「還不確定」的事。誠實留著，不要為了好看而自己填答案]
```

**brief 不寫**：系統行為細節（那是 PRD）、任務狀態與進度（WBS）、實作做法（plan）、技術選型理由（ADR）。

# 下半：`docs/prd.md`

```markdown
# [專案名稱] PRD

> 讀者：開發者、客戶、agent ・ 情境由 /verify 依 plan 套回，不手寫進度

## 用語表

| 用語 | 意思 | 不要說成 |
|---|---|---|
| 訂單 | 使用者按下結帳後產生、尚未出貨的購買紀錄 | 單子、order |

## 功能

### 結帳（模組分組：服務層）

#### ORD-01 正常結帳
- 假設 購物車有 2 件商品、使用者已登入
- 當 使用者按「結帳」
- 那麼 建立一筆訂單，購物車清空

#### ORD-02 庫存不足
- 假設 其中一件商品庫存為 0
- 當 使用者按「結帳」
- 那麼 不建立訂單，畫面指出缺貨的商品

### 會員（模組分組：用戶端）

#### MEM-01 註冊
- 假設 使用者尚未註冊、Email 未被使用
- 當 使用者送出註冊表單
- 那麼 建立帳號，並寄出驗證信

## 非功能需求（選填）

- [效能、安全、可用性等有具體數字的要求；沒有就刪掉這節]

## 待確認

- [待確認] [還沒決定的問題]
```
```

**寫法**：

- 每條情境一個 `#### <代碼>-<序號> 標題`，下面三行「假設／當／那麼」，需要時用「而且」續行。**編號永不重用**，刪除的編號不補
- 功能依**領域**分節；節標題括號寫**模組分組名**，必須等於架構文件自動段的「分組」欄（也是專案地圖的群組框）
- 用語表在最前面：PRD、plan、程式碼的命名都用表裡的詞；「不要說成」欄防止同一件事三種叫法
- `[待確認]` 只出現在「待確認」一節，不散落在情境裡
- 變更：plan 的「PRD 情境變更」列出這次增（ADDED）、改（MODIFIED）、刪（REMOVED）的情境，`/verify` 套回本檔；格式見 `plan-format` skill

**PRD 不寫**：

| 不寫 | 它的唯一來源 |
|---|---|
| 產品方向、不做什麼 | brief |
| 實作細節、檔案路徑、API 端點清單 | 程式碼、plan |
| 進度、完成日期、plan 或 WBS 編號 | WBS |
| 設計理由 | ADR |
| 模組、依賴、路由數 | 程式碼（架構文件自動段） |
