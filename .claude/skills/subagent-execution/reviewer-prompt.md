# reviewer-prompt — 階段審查骨架

階段審查分兩層，**分開送**：

1. **規格合規**（本檔）— 做的是 plan 說的事嗎？驗收達成了嗎？有沒有多做？
2. **程式品質** — 委派 `code-quality-specialist`，不用本骨架（那個 agent 有自己的流程）

規格合規審查用 `subagent_type: "general-purpose"`，模型與被審階段同級（複雜階段往上一級）。

---

## 為什麼規格合規要單獨審

`code-quality-specialist` 審的是「這段程式碼好不好」，它**不知道 plan 說了什麼**。
一段寫得很漂亮但做錯事的程式碼會通過品質審查。反之，規格合規審查不管命名與結構，
只管「這是不是我要的東西」。兩者都不能取代對方。

```
implementer 的回報：
<貼它的 STATUS 區塊>

## 你要回答四個問題

1. **驗收達成了嗎？** 逐條對驗收條件打勾或打叉，打叉要指出缺什麼
2. **做的是規格說的事嗎？** 有沒有做了規格沒說的事（範圍蔓延）？有沒有把規格說的事做成別的？
3. **有沒有動到授權範圍外的檔案？** 有就列出來
4. **測試真的有測到這個階段的行為嗎？** 「有測試」不等於「測對」——
   看斷言在斷什麼，不要只看覆蓋率數字

## 判準

- 只報你有 **>80% 信心**的問題。猜測不要寫
- 分級：`BLOCKING`（驗收未達成／做錯事／越權改檔）、`NON_BLOCKING`（可以下階段再處理）
- **不要**報命名、格式、結構問題——那是 code-quality-specialist 的範圍，你重複報只會製造噪音
- 規格本身自相矛盾或漏講 → 明確指出是**規格**的問題，不是實作的問題

## 回報格式

STATUS: DONE
判定：PASS | FAIL
驗收逐條：
  - <條件 1>：✅ / ❌ <為什麼>
BLOCKING 問題：
  - <問題><在哪個檔案哪一行><為什麼違反規格>
NON_BLOCKING 觀察：
  - <觀察>
越權改檔：<清單，或「無」>
規格缺陷：<若規格本身有問題，寫在這裡；否則「無」>
```

## 主模型收到審查結果之後

| 審查結果 | 做什麼 |
|---|---|
| `PASS`，無 BLOCKING | 帳本記完成 → plan 階段標 ✅ → `current_phase++` → 下一階段 |
| 有 BLOCKING | 進修復迴圈（R1-R3 交回同一個 implementer；R4-R5 換新的並升級模型） |
| 只有 NON_BLOCKING | 記進帳本當技術債，繼續。**不要**為了清乾淨而多跑一輪 |
| 回報「規格缺陷」 | **你裁決**：改 plan 還是照原樣做。裁決記進帳本，帶著裁決重新派工 |
| BLOCKING 與 plan 文字衝突 | 同上，你裁決。不要讓 implementer 去猜該聽誰 |
