# NoSQL 模式（文件型）

**這裡的規則跟 SQL 相反的地方比相同的多。** 正規化、join、「先設計 schema 再想查詢」
在文件資料庫全部不適用 —— 那是本檔存在的理由。

關聯式的作法見 `.claude/skills/sql-patterns/SKILL.md`。

## 啟動時機

- 設計 MongoDB／Firestore 的 collection 與文件結構
- 查詢變慢，或 **Firestore 帳單變貴**（這兩件事在文件資料庫是同一件事）
- 決定某段資料要嵌入（embed）還是另開 collection（reference）
- 從 SQL 專案遷移過來，或反之

---

## 第一原則：存取模式先行

SQL 的順序是「設計正規化 schema → 需要什麼就 join 出來」。
文件資料庫**沒有 join**，所以順序反過來：

```
1. 先列出應用實際會發的每一種查詢（包含排序與過濾條件）
2. 設計文件結構讓「每個畫面一次讀取就拿到所需資料」
3. 才決定要不要反正規化
```

**跳過第 1 步是文件資料庫最常見、也最貴的錯。** 結構定了之後改，
意味著要寫遷移程式碼跑過所有既有文件。

## embed 還是 reference

| 選 embed（嵌進父文件） | 選 reference（另開 collection） |
|---|---|
| 幾乎總是跟父文件一起被讀 | 常常單獨查詢 |
| 數量**有界且小**（訂單的 3 個項目） | 數量無界會成長（貼文的留言） |
| 更新頻率跟父文件差不多 | 更新頻率遠高於父文件 |
| 不需要被獨立查詢或排序 | 需要跨父文件查詢（「所有未讀通知」） |

**判準：無界成長的陣列一律不要 embed。** MongoDB 單一文件上限 16MB，
Firestore 是 1MB —— 但真正的問題在到達上限之前就出現了：
每次讀父文件都要傳整個陣列，每次改一個元素都要寫回整份文件。

```javascript
// ❌ 留言會無限成長
{ _id: 1, title: "...", comments: [ /* 五千筆 */ ] }

// ✅ 留言另開 collection，父文件只留計數
{ _id: 1, title: "...", commentCount: 5000 }
```

## 反正規化是刻意的取捨，不是偷懶

複製資料（把 `authorName` 一起存進貼文）在文件資料庫是**正常做法** ——
代價是作者改名時要更新所有貼文。

決定前先問：**這個欄位多久會變？變了之後舊資料不同步能接受多久？**

- 幾乎不變（使用者 ID、建立時間）→ 放心複製
- 偶爾變且要求最終一致（顯示名稱）→ 複製，寫背景任務修正
- 常變且要求即時正確（庫存、價格、餘額）→ **不要複製**，用 reference

## 索引

**兩個引擎都必須明確建索引** —— 沒有「引擎自動幫你想辦法」這回事。

- **MongoDB**：用 `explain()` 看有沒有走索引。複合索引同樣看**最左前綴**，
  且順序要配合排序方向。`$regex` 非前綴錨定時走不了索引
- **Firestore**：單欄位索引自動建；**任何多條件或含排序的查詢都需要 composite index**，
  沒有的話查詢直接失敗並回傳一個建立連結。**這是好事** —— 錯誤發生在開發期而非上線後

## 分頁一律用 cursor，不要用 skip

```javascript
// ❌ skip 要掃過並丟棄前面所有文件，愈後面愈慢（Firestore 還照掃過的文件計費）
db.posts.find().sort({_id: 1}).skip(10000).limit(20)

// ✅ 用上一頁最後一筆當游標
db.posts.find({_id: {$gt: lastId}}).sort({_id: 1}).limit(20)
```

Firestore 用 `startAfter(lastDoc)`。

---

## Firestore 專屬：設計直接決定帳單

Firestore **按讀取的文件數計費**，不是按查詢次數。這讓「資料模型」和「成本」變成同一件事：

- 一個畫面要讀 100 份文件 → 每次開啟就是 100 次計費讀取。
  **把要一起顯示的資料放進同一份文件，可以直接把成本降兩個數量級**
- 計數不要靠「讀全部再 `.length`」→ 存一個計數欄位，用
  `FieldValue.increment()` 更新（原子操作，不需先讀）
- **單一文件的持續寫入頻率上限約每秒一次**。計數器熱點要用
  **sharded counter**（拆成 N 個子文件隨機寫，讀時加總）

## MongoDB 專屬注意

- 寫入確認等級（write concern）要明確設定；預設值隨版本與部署方式變動
- 交易可用（4.0+ replica set），但**跨文件交易的成本遠高於 SQL**。
  能用單文件原子更新解決的就不要開交易
- 聚合管線（aggregation）盡量把 `$match` 放最前面，讓它能用索引

---

## 最終一致性

副本讀取可能拿到舊資料。**寫入後立刻讀取不保證看到自己剛寫的值**，除非明確要求。

實務影響：使用者按「儲存」後馬上重新整理，可能看到舊值。
處理方式是前端樂觀更新（optimistic update）或明確指定強一致讀，不要假設它不會發生。

## 反模式

- ❌ 把 SQL 的正規化 schema 一對一搬過來，然後在應用層做 join
- ❌ 無界成長的陣列 embed 在文件裡
- ❌ 用 `skip`／`offset` 做分頁
- ❌ 先設計文件結構、才想查詢
- ❌ 靠讀取全部文件來算數量（Firestore 這樣做又慢又貴）
- ❌ 對單一文件高頻寫入（計數器熱點）而不 sharding
- ❌ 假設寫入後立刻讀得到
