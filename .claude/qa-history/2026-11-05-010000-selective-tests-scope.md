# 依改動挑節的範圍（2026-11-05）

背景：審查「hook 測試依改動挑節」（6d1e852）時發現兩個問題。
- 一新增測試就會改到 `run-tests.sh`，照目前的規則會跑整套；在 worktree 裡跑時，還會繞過閘門。
- `verify.md` 會複製到所有新專案，等於一般專案也會被改成依改動挑節。

## Q1 改到 run-tests.sh 時要跑什麼？
- 選項：
  - 只跑被改到的節 (Recommended)
  - 維持跑整套，只補閘門
- 答案：只跑被改到的節

## 釐清：為什麼在 Windows 跑 hook 比較久？
- Windows 沒有 fork，Git Bash（MSYS2）用模擬的方式開程序，再加上防毒軟體掃描，每開一個程序約 0.14 秒。
- 一次 hook 會開幾十個程序，所以要幾秒；869 個測試加起來約 51 分鐘。
- 使用者確認：只有改模板時才需要跑這套測試。一般專案的 pytest、jest 不會慢成這樣，但一般專案仍然要負擔每次寫檔時 hook 的幾秒鐘。

## Q2 新專案的 /verify 合併後要怎麼跑測試？
- 選項：
  - 維持跑整套 (Recommended)
  - 依整套耗時自動切換
  - 所有專案都依改動挑
- 答案：維持跑整套

## 結論
- 「依改動挑節」只用在模板 repo 自己的 hook 測試。
- 改到 `run-tests.sh` 時用 diff 行號判斷改到哪幾節；在 worktree 裡如果判定要跑整套，就拒絕執行，必須加 `--full` 才跑。
- 新專案的 `/verify` 照舊在每輪最後一次合併時跑整套。
- 已請原本的 agent 在同一個分支修正，並一起處理審查的其餘 MEDIUM 與 LOW。
