# 編碼風格

## 克制原則（CRITICAL）

只做被要求的事，用最簡單可行的方式做好：

- 不加任務範圍外的功能、重構或抽象；修 bug 不順手清理周邊
- 不為「不可能發生的情境」寫錯誤處理/fallback/驗證——只在系統邊界驗證（使用者輸入、外部 API）
- 不為假想的未來需求設計；一次性操作不需要 helper
- 註解預設不寫 —— 見下方「註解」小節
- 修 bug 先 `rg` 被改函式的所有呼叫端，在共用處修一次根因，不在各呼叫端各補
- 收尾時用一行交代：跳過了什麼、沒驗證什麼、有什麼風險（都沒有就省略；subagent 寫進 STATUS 區塊，不另起一行）

## 註解（CRITICAL）

**預設不寫。** 註解會過期、會跟程式碼說謊；只有當它承載程式碼本身表達不了的資訊時才值得寫。

### 只在這四種情況寫

| 情況 | 例 |
|---|---|
| **為什麼**這樣做（非顯而易見的取捨） | `// 用輪詢而非 webhook：對方 API 沒有重送機制` |
| 外部約束、workaround、踩過的雷 | `// Safari 17 的 flex gap 有 bug，改用 margin` |
| 魔法數字的來源 | `// 0.7 = 供應商文件建議的相似度門檻` |
| 公開 API 的合約中型別表達不了的部分 | 拋出條件、副作用、單位 |

### 絕不寫

- 逐行/逐段敘述程式在做什麼 —— 那是程式碼的工作
- 覆述函式名或變數名的「說明」
- 區塊分隔標題（`// ---- 初始化 ----`）—— 需要它就代表函式該拆了
- 被註解掉的舊程式碼、變更紀錄、署名 —— 交給 git
- 沒有 issue 連結的 TODO

> **判準：把註解刪掉，讀者會不會失去資訊？** 不會 → 刪掉。
> 想用註解解釋一段程式在幹嘛時，優先改名或抽函式，而不是加註解。

## 先研究再實作

寫新程式前依序找，第一個能完整解決的就用：
**專案裡已有**（`rg` 過一遍，照周邊程式的用法）→ **標準庫／平台原生功能** →
**已安裝的套件**（不為幾行程式引進新依賴）→ **一行寫得完** → 才自己寫。
用到函式庫 API 時查官方文檔（`context7` MCP），不憑記憶。
選了哪一層要講出來；「找了一下沒有就自己寫」不算研究過。

## 不可變性（CRITICAL）

永遠建立新物件，絕不修改既有物件：使用 spread operator / 不可變方法。
不可變資料防止隱藏副作用、簡化除錯、確保並行安全。

## 檔案組織

拆檔看**職責**不看行數：一個檔能用一句話說出在做什麼（句子裡不需要「和／以及」），只因一種原因被修改。
約 800 行時停下來複查職責；確定單一就不拆。不按位置切成前後兩半、不建沒有主題的 `utils`／`helpers`／`common`。
依功能/領域組織，非依類型。

## 錯誤處理

每層明確處理、絕不靜默吞錯；UI 給友善訊息、伺服器端記完整上下文。驗證只在系統邊界（同克制原則）。
API 回應信封見 `api-design` skill。

## Commit Message

```
<type>: <description>

<optional body>
```

Types: `feat` `fix` `refactor` `docs` `test` `chore` `perf` `ci`

> 留在常駐 rule 是因為 commit 常是順手做的、沒有關鍵字可喚起 skill。PR 流程見 `.claude/commands/pr.md`（唯一來源）。

## Bash 工作目錄

Bash tool 的 CWD 跨呼叫持續存在。優先用絕對路徑；需要切目錄時用 subshell
`(cd subdir && npm test)` 或鏈式 `cd subdir && npm test`。
**裸 `cd` 會被 `pre-tool-use.sh` 擋下**（逃生門：`TASKMODE_GATE=off`）。

## Context Window 管理

剩餘 context 低於 20% 時不做大規模重構或跨多檔的實作。**在階段邊界 compact，不在實作中間。**
compaction 後只剩檔案系統上的東西（rules、todo、git 狀態、你寫進檔案的內容），
所以**先落地再壓**——決策寫 `context/decisions/`、跨 session 先 `/save-session`。
