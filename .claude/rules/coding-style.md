# 編碼風格

## 克制原則（CRITICAL）

只做被要求的事，用最簡單可行的方式做好：

- 不加任務範圍外的功能、重構或抽象；修 bug 不順手清理周邊
- 不為「不可能發生的情境」寫錯誤處理/fallback/驗證——只在系統邊界驗證（使用者輸入、外部 API）
- 不為假想的未來需求設計；一次性操作不需要 helper
- 註解只寫程式碼本身無法表達的約束，不逐行敘述程式在做什麼

## 先研究再實作

任何新實作前：先搜現有實作與官方文檔（`context7` MCP 查函式庫文檔），
找得到經驗證的方案就採用，不從零重寫。

## 不可變性（CRITICAL）

永遠建立新物件，絕不修改既有物件：使用 spread operator / 不可變方法。
不可變資料防止隱藏副作用、簡化除錯、確保並行安全。

## 檔案組織

多個小檔案 > 少數大檔案：200-400 行典型，800 行上限。
依功能/領域組織，非依類型。高內聚、低耦合。

## 錯誤處理

- 每個層級明確處理錯誤
- UI 面向使用者的友善錯誤訊息
- 伺服器端記錄詳細錯誤上下文
- 絕不靜默吞噬錯誤

## 輸入驗證

在系統邊界驗證：驗證所有使用者輸入、使用 schema-based 驗證、
快速失敗並給清晰錯誤訊息、永遠不信任外部資料。

## API 回應格式

所有 API 使用一致的信封格式：成功/狀態指示器、資料酬載（錯誤時 null）、
錯誤訊息欄位（成功時 null）、分頁中繼資料（total, page, limit）。

## Bash 工作目錄

Bash tool 的 CWD 跨呼叫持續存在。優先用絕對路徑；需要切目錄時用 subshell
`(cd subdir && npm test)` 或鏈式 `cd subdir && npm test`。
**裸 `cd` 會被 `pre-tool-use.sh` 擋下**（逃生門：`TASKMODE_GATE=off`）。

## Context Window 管理

剩餘 context 低於 20% 時避免：大規模重構、跨多檔案的功能實作、複雜互動除錯。
低 context 適合：單檔案編輯、獨立工具函式、文檔更新、簡單 bug 修復。

## 品質檢查清單

- [ ] 程式碼可讀、命名良好
- [ ] 函式 < 50 行
- [ ] 檔案 < 800 行
- [ ] 無深層巢狀 (> 4 層)
- [ ] 適當錯誤處理
- [ ] 無硬編碼值
- [ ] 不可變模式
