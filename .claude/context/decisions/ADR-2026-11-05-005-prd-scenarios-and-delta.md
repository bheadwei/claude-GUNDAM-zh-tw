# ADR-2026-11-05-005: PRD 用編號的中文情境（假設／當／那麼）加用語表寫成；plan 記下這次增、改、刪了哪幾條，`/verify` 由模型套回 PRD

## 背景

現在的 PRD 寫完就不再更新，之後的變更只寫在 plan 裡。`spec-convergence` 找得到落差，
但它的規則是「不改 PRD」，所以落差只會被報告、不會消失。實測專案 B 的主架構文件開頭有一段「之後的變更（先讀這段）」，
下面 900 行是舊文；A 有 9 份現行文件帶「與舊文不符」附錄。

研究查到的工具裡，只有 OpenSpec 有讓規格跟著現況走的機制：每個變更只寫差異（ADDED／MODIFIED／REMOVED），
完成時把差異套回現況規格（2026-11-05 查證：官方 repo 與二手說明一致）。但它要裝 CLI、另開 `specs/` 與 `changes/` 目錄。

使用者要 PRD「人看得懂」、跟著現況走，但不要新工具、新腳本、新 hook。
PRD 要寫成什麼樣子，又由誰在什麼時候更新？

## 決策

**PRD 格式**（`docs/prd.md`，範本在 02 的下半部）：

```markdown
# <專案名> PRD

> 讀者：開發者、客戶、agent ・ 情境由 /verify 依 plan 套回，不手寫進度

## 用語表
| 用語 | 意思 | 不要說成 |
|---|---|---|
| 訂單 | 使用者按下結帳後產生、尚未出貨的購買紀錄 | 單子、order |

## 功能

### 結帳（模組分組：服務層）
#### ORD-01 正常結帳
- 假設 購物車有 2 件商品、使用者已登入
- 當 使用者按「結帳」
- 那麼 建立一筆訂單，購物車清空

#### ORD-02 庫存不足
- 假設 其中一件商品庫存為 0
- 當 使用者按「結帳」
- 那麼 不建立訂單，畫面指出缺貨的商品

## 非功能需求（選填）
## 待確認
```

- 每條情境一個 `#### <代碼>-<序號> 標題`，下面三行「假設／當／那麼」，需要時用「而且」續行。**編號永不重用**（同 WBS）
- 功能依**領域**分節；領域就是 DDD 的模組邊界，**名稱等於架構文件模組表的「分組」、也就是地圖上的群組框**（節標題括號寫分組名）。DDD 只取這一點和用語表，不做聚合、領域事件
- 用語表：PRD、plan、程式碼的命名都用表裡的詞；「不要說成」欄防止同一件事三種叫法
- **不寫**：實作細節、檔案路徑、API 端點清單、進度、plan 或 WBS 編號
- `[待確認]` 只出現在「待確認」一節

**情境變更**：plan 的「為什麼做」底下有一小節「PRD 情境變更」（ADR-006），只列這次動到的情境：

```markdown
### PRD 情境變更
- ADDED ORD-03 部分出貨 —（假設／當／那麼全文）
- MODIFIED ORD-02 庫存不足 —（改後的全文）
- REMOVED ORD-05 —（理由一句）
```

沒有動到使用者看得到的行為就寫「無」。

**套回**：沿用 `/verify` 既有的「文件同步關卡」，多一項檢查：
目前任務的 plan 有情境變更、而且還沒套回 → **主模型自己改 `docs/prd.md`**（ADDED 加到對應領域節末、MODIFIED 依編號整條取代、REMOVED 刪除），
套完在該小節末加一行 `已套回 PRD（YYYY-MM-DD）`，有這行就不重做。
這項和「標記與歸檔」一樣**只在主 checkout 做**；worktree 裡的 `/verify` 跳過，合併完回主 checkout 再做，所以平行開發不會在 PRD 上衝突。

**不做**：`specs/` 目錄、`spec-merge.sh`、`docs-lint.sh`、任何新 hook、裝 OpenSpec CLI。
套回是寫字的工作、數量小（一個 plan 通常 1–5 條），由正在跑 `/verify` 的主模型順手做，不需要另一支程式或另一個 agent。

**其他規則**：
- `/plan` 寫情境變更時，planner 先在其他進行中的 plan 裡找同一個編號，有就在 plan 裡提一句（不擋）
- quick 任務沒有 plan：若改到 PRD 某條情境描述的行為，直接改那一條（PRD 是 `.md`，不受判級閘門攔）
- `spec-convergence`：輸入改成 brief → PRD → WBS／plan → 程式碼；檢查 C（描述失真）比的是 PRD 情境與程式碼；
  它仍然不直接改 PRD——PRD 只透過 plan 的情境變更改，因為那些變更在 `/plan` 時已經讓使用者看過

## 替代方案

| 方案 | 優點 | 否決理由 |
|---|---|---|
| 維持現狀（PRD 一次性，落差靠 `spec-convergence` 報告） | 不用改 | 落差只會累積；A、B 的勘誤附錄就是這樣長出來的 |
| 照 OpenSpec：`docs/specs/<領域>.md` ＋ `spec-merge.sh` 機械合併 | 0 token、可重跑 | 多一個目錄、一支腳本、一套測試；人要翻好幾個檔才看得懂系統。使用者明確不要 |
| 直接裝 OpenSpec CLI | 現成 | 要 Node；它的目錄與流程和 task-next／plan／verify 重疊，等於兩套流程 |
| EARS 句型（「當…，系統必須…」）取代情境 | 一行一條、短 | 客戶與非開發者讀「假設／當／那麼」比較容易對到自己的操作；需要精確規則時可以寫在「那麼」裡 |
| 另開一份 BDD 文件放情境 | 跟 BDD 工具習慣一致 | 又多一份；情境本來就是需求的寫法，放 PRD 裡就好 |
| 實作前就先改 PRD | PRD 永遠反映「打算做的」 | 做到一半放棄或改方向時，PRD 描述的是不存在的行為 |

## 後果

**得到：**
- PRD 是一份人看得懂、跟著每個完成的 plan 更新的「系統現在做什麼」
- plan 的驗收句直接引用情境編號，不用另寫驗收清單
- 沒有新的程式要維護

**犧牲：**
- 套回靠模型照做，沒有機器檢查。緩解：它在 `/verify` 的固定關卡裡，而且「已套回」那一行讓遺漏看得出來
- 兩份進行中的 plan 改同一條情境時，後套回的會蓋掉先套回的；`/plan` 的同編號提醒只是提醒
- 情境寫得太細會讓 PRD 變長；一個領域超過約 20 條時，該想的是拆領域，不是加附錄

**何時該重新考慮：**
- 抽查發現完成的 plan 有兩成以上沒套回 PRD → 那時再考慮讓 `/verify` 的機器檢查介入（例如 `overview.sh` 順帶算「有情境變更但沒有『已套回』的歸檔 plan」數）
- PRD 超過約 600 行 → 改成按領域拆檔，PRD 只留用語表與索引

## 確認方式

- [M] 用一個範例專案跑完 `/plan` → `/tdd` → `/verify`：PRD 多了那條 ADDED、plan 小節末有「已套回」、plan 已歸檔
- [M] 在 worktree 跑 `/verify`：PRD 沒被改；合併後在主 checkout 跑 `/verify` 才套回
- [C] `check-counts.sh`：02 範本的 PRD 骨架有「用語表」「功能」兩節，範例情境的編號符合 `^[A-Z]+-[0-9]+`
