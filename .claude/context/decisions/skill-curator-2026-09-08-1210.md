## 為什麼一個都沒搬

這 19 個是一個社群 repo 的「agent 工程方法論」層。本 repo 在同一層已經有
15 個 agent、7 支 hook、`writing-extensions`、`subagent-execution`、
`worktree-orchestration`、`check-counts.sh`（293 項檢查），而且**多數是機器強制的**
（deny 閘門、additionalContext 注入），備份池那批全部是給模型讀的文字。

同一件事的較弱版本搬進來只會多一份要維護、且會與唯一來源漂開的表。
所以取材方式是**只挖出這個 repo 缺的具體段落，併進既有檔案**。

其中五個（`configure-ecc`、`nanoclaw-repl`、`dmux-workflows`、`blueprint`、
`ralphinho-rfc-pipeline`）如預期綁死他們自己的工具鏈，見下表逐一。

## 需使用者判斷

1. **要不要做「hook 觀察 → 學習」這個方向**（`continuous-learning-v2` 的路線）。
   本次判 Retire 的理由是「維護 3748 行子系統」，不是「方向錯」。
   本 repo 已有 `/learn` ＋ 坑閘門，但**抽取仍靠人記得下指令**。
   若要做，正確做法是自己寫一支輕量 PostToolUse 觀察 hook，不是搬他們的。
   → 這件事本身該由使用者決定要不要開一個任務，我不自行決定。
2. **`strategic-compact` 的 hook 那一半要不要補**：時機是機器判斷得出的，
   按決策表該做成 hook（工具呼叫數／context 比例觸發提示）。
   本次因「不要動 hook」的指示而只吸收了文字。
   → 若要做，是 `post-write.sh` 或新的 PostToolUse 計數器，需與使用者正在改的 hook 協調。
3. **備份池刪除前**：本次只盤了 19 個 agent 工程類，剩下 75 個未盤。
   刪之前那 75 個要不要各跑一輪同樣的盤點？
4. **`.skill-impact` 沒清乾淨（刻意）**：清單裡有一筆
   `.claude/skills/ui-style-compliance/SKILL.md` **不是我改的**（本 session 期間由使用者改動，
   看起來與新增 `.claude/ui/semrush/` 是同一件事）。我只移除自己那四筆，那一筆留著等後續處理，
   否則會把使用者在飛的變更從清單上抹掉。
