# ADR-2026-11-05-008: 既有專案的舊文件走「按需盤點 → 對到 6 份 → 逐批同意後 `git mv`」，不自動改寫或刪除任何使用者文件

## 背景

ADR-004 到 007 改的是模板。已經有 75–85 份 `docs/` 文件的既有專案（實測 A、B）跑 `update-template` 之後，
`docs/` 不會有任何變化（update-template 不碰專案文件）。這兩個專案最痛的問題（找不到現況、入口死連結、
同一主題多份成品、新舊並存）都在既有文件裡。但這些文件屬於使用者，部分是已交付給客戶的版本，
模板不能替使用者決定哪份是正本。既有專案要怎麼收斂到 6 份？

## 決策

分四步，**每一步都是按需的，不由 hook 觸發，也不新增指令或腳本**：

| 步 | 誰 | 做什麼 | 寫入什麼 |
|---|---|---|---|
| 0 | 不需要任何動作 | 專案地圖、一頁現況、架構文件自動段（ADR-007）只讀程式碼、WBS、plan，**不依賴文件收斂**，升級後立刻可用 | 無 |
| 1 | `documentation-specialist`（使用者同意後才派） | 用 `git ls-files docs/`、`git log -1 --format=%cs` 列出每份文件的路徑、行數、最後修改日；讀每份開頭最多 40 行 | 無 |
| 2 | 同上 | 每份文件分到四類之一，寫成報告 | 報告 `context/docs/docs-inventory-<日期>.md`（**不碰 `docs/`**） |
| 3 | 主模型，逐批 AskUserQuestion | 照報告分批 `git mv`、修好因此斷掉的 repo 內連結；每批一個 commit | 只搬檔與改連結 |

**分類（對到 6 份）**：

| 類 | 判準 | 建議去處 |
|---|---|---|
| 併入 6 份之一 | 內容是需求、架構、決策、進度、計畫（例：舊 PRD、`tech-spec.md`、單檔多條 ADR、第二份 WBS） | 新文件的**草稿來源**；原檔搬到 `docs/archive/` |
| 現行，模板外 | 交付物、對外手冊、評測與弱掃紀錄、匯出檔 | **留在原處**，報告只列出、不建議搬 |
| 封存 | 過期、被取代、和程式碼對不上 | `docs/archive/` |
| 重複 | 同一主題多份成品 | 報告指出哪份最新、其餘建議封存；同一數字多種版本時列出各種寫法與出處 |

報告另列：入口文件（`README.md`、`CLAUDE.md`、`docs/README.md` 若有）的失效路徑、建議的搬移批次（每批 ≤ 15 檔、同一類）。

**入口**：`/docs-init` 偵測到既有文件（`docs/` 有 5 份以上不是 6 份之一的 md，或沒有 `docs/00_brief.md` 卻有其他文件）時，
第一題就問要不要先盤點（Recommended）。**不新增指令**，掛在既有的 `/docs-init`（使用者偏好整合進既有流程）。

**內容轉換是另一個選項，永遠要使用者確認**：例如「從舊 PRD 起草新格式的 `docs/prd.md`（情境＋用語表）」、
「把單檔多條 ADR 拆成 `docs/decisions/` 一條一檔」、「從舊架構文件抽出人寫的三節」，
由 agent 起草、使用者逐份確認後才寫。**舊文件只在使用者同意時搬到 `docs/archive/`，任何情況下都不刪除；交付物一個字都不改。**

## 替代方案

| 方案 | 優點 | 否決理由 |
|---|---|---|
| 不提供遷移，只套用到新文件 | 零風險 | A、B 的問題全在既有文件，等於沒解決 |
| `update-template` 時自動搬檔與改寫 | 一步到位 | 分類（哪份是正本、哪份已交付）是人的決定，搬錯交付物代價很高 |
| 寫一支盤點腳本（列路徑、日期、死連結） | 0 token | 使用者明確不要新腳本；列檔與日期兩個 git 指令就做得到，交給已有 Bash 的 agent |
| 交付物、紀錄搬進 `docs/deliverables/`、`docs/records/` | 位置一致 | 又多兩種模板要管的位置；交付物在原處對使用者最不會出錯 |
| 新增 `/docs-migrate` 指令 | 入口清楚 | 使用者偏好掛進既有流程；`/docs-init` 本來就是「建立或補齊文件」的入口 |
| hook 偵測到舊文件就派 agent 盤點 | 不用人記得 | 背景開不了模型；讀幾十份文件要花 token，必須使用者明確同意；使用者不要新 hook |

## 後果

**得到：**
- 升級後第一天就有地圖與一頁現況，不必先整理文件
- 使用者拿到一張「每份文件是什麼、該併進哪一份或封存」的表，自己決定收斂到什麼程度
- 搬移有 commit 紀錄，可以整批還原

**犧牲：**
- 盤點一次約讀 75–85 份文件的開頭，估 60k–120k 輸入 token
- 收斂進度取決於使用者願意同意幾批；模板不保證既有專案會收斂完成
- 搬檔會讓外部書籤或其他 repo 的連結失效（repo 內的連結由第 3 步修好）

**何時該重新考慮：**
- 使用者多半在報告之後就停住 → 把批次做得更粗（一次同意整類）
- 人工抽查分類錯誤超過兩成 → 第 2 步改成先問使用者幾個關鍵問題（例如「哪幾份交給客戶過」）再分類

## 確認方式

- [M] 在一個有既有文件的專案跑一次 `/docs-init`：第一題是盤點；報告產出後 `git status` 沒有任何 `docs/` 的變更
- [M] 同意第一批後，那個 commit 只有 rename 與連結修正（`git show --stat -M` 全是 `=>`，加上連結所在檔的少量行數）
- [M] 報告與起草的文件不含實測專案的客戶名、內部代號、IP（沿用 module-notes 的機密樣式清單人工抽查）
