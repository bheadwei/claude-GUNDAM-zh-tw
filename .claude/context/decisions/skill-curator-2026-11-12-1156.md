```markdown
## 克制原則（CRITICAL）

只做被要求的事，用最簡單可行的方式做好：

- 不加任務範圍外的功能、重構或抽象；修 bug 不順手清理周邊
- 不為「不可能發生的情境」寫錯誤處理/fallback/驗證——只在系統邊界驗證（使用者輸入、外部 API）
- 不為假想的未來需求設計；一次性操作不需要 helper
- 註解預設不寫 —— 見下方「註解」小節
- 修 bug 先 `rg` 被改函式的所有呼叫端，在共用處修一次根因，不在各呼叫端各補
- 收尾時用一行交代：跳過了什麼、沒驗證什麼、有什麼風險（都沒有就省略；subagent 寫進 STATUS 區塊，不另起一行）
```

### 「先研究再實作」整節改成

```markdown
## 先研究再實作

寫新程式前依序找，第一個能完整解決的就用：
**專案裡已有**（`rg` 過一遍，照周邊程式的用法）→ **標準庫／平台原生功能** →
**已安裝的套件**（不為幾行程式引進新依賴）→ **一行寫得完** → 才自己寫。
用到函式庫 API 時查官方文檔（`context7` MCP），不憑記憶。
選了哪一層要講出來；「找了一下沒有就自己寫」不算研究過。
```

### 為什麼這樣寫

- (b) 的「不在各呼叫端各補」與既有「修 bug 不順手清理周邊」不衝突：前者是**修法的位置**，後者是**範圍**。
- (c) 原文是「End your reply with…」。直接照搬成「最後一行」會撞上 14 個 agent 的回報格式——每個都規定「最後一行（或最後一段開頭）必須是 STATUS 碼」，而 rules 會載進 subagent。所以寫成「收尾時用一行」並明講 subagent 寫進 STATUS 區塊。「都沒有就省略」避免每則回覆都多一行「無風險」。它與 output style「先講結論」相容（一個管開頭、一個管結尾）。
- (a) 原有的「採用／包一層薄的／組合兩三個小的／自己寫」四選一被 ponytail 的五層取代——五層有順序，比四個並列選項更能直接執行。
- 量：克制原則 +260 B、先研究再實作 526 → ~400 B，**淨 +約 150 B**。
- 刻意不採的 ponytail 條文：`shortcut:` 註解（與「註解只寫四種情況」衝突，使用者已排除）、Levels（我們的分級是 task-mode，不需要第二套）、「Lazy code without its check is unfinished」（`testing-standards`／task-mode 已涵蓋）。
