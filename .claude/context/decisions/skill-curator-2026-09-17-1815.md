# 平行開發的兩個隔離缺口：分支拓撲（checkout -b）與執行層隔離（symlinkDirectories）

## TL;DR
- 新增 `lib/branch-switch-gate.sh`：站在非預設分支上 `git checkout -b`／`git switch -c` 會被擋。
  有 in-flight agent 時**持續擋**（會抽掉它腳下的分支），沒有時**擋一次**（基底會混進前一個任務）。
- in-flight 計數抽成 `lib/agent-inflight.sh`，`pre-agent-gate.sh` 與新閘門共用；pre-agent-gate 行為不變。
- **`worktree.baseRef` 查證後決定不改**，維持 `"head"`——只有 `fresh`／`head` 兩個合法值，
  改成 `fresh` 會打破模板既有且有明確理由的設計（plan 還沒 push，worktree 會讀不到）。
- **`worktree.symlinkDirectories` 預設改成 `[]`**（原本五項全移除）：symlink 環境目錄／建置產物
  會讓帶隔離的 agent **靜默執行到另一條線的程式碼**。判準寫進 skill，新寫一篇 learned。
- hook 測試 **356 通過 0 失敗**（新增 34 案例 + 2 支 lib 的語法案例）、`check-counts.sh --tests 356` 316 項全一致。
- **未做行為驗證**（沒跑 skill-compliance）。兩道機器層變更（閘門、設定預設值）不需要；
  但 `git-workflow.md`／`agent-orchestration.md`／skill 的文字改動只有接線檢查，沒有行為證據。

## 範圍
- **觸發原因**：使用者在實際專案平行開發時的兩起事故（2026-09-17）
  1. 主 checkout 站在 `fix/stream-token-ledger`、一個 subagent 正在那條分支上工作，
     此時要開第二個任務。模型第一反應是「不能平行」，被追問後才講出真正的原因
     （「`git checkout -b` 會把它腳下的分支抽掉」）。**講得出危險，但是在被推了之後**，
     沒有任何機制在它真的要打那條指令時攔下來。
  2. 切到 topic 分支之後遇到新任務，不會想到要切回預設分支再開 → 新分支的基底
     混進前一個任務的 commit。
- **參考資料**：`writing-extensions` 五層決策表（第一列：判斷得出時機就用 hook）、
  `lib/git-backup-gate.sh` 檔頭對「擋狀態 vs 擋資訊」兩種閘門的區分、
  `lib/cmd-segments.sh` 檔頭對子字串比對的教訓、`lib/merge-noff-gate.sh` 的形狀
- **層級判斷**：這兩件事都有「一個機器判斷得出來的時機」（Bash 工具收到 `git checkout -b` 的當下），
  所以是 **Hook（PreToolUse）**，不是 rule。`rules/git-workflow.md` 只寫一句「由閘門強制」。

## 發現與處置

### 🔴 High — 沒有任何機制擋住「抽掉別人腳下的分支」

新檔 `.claude/hooks/lib/branch-switch-gate.sh`，接線進 `pre-tool-use.sh` 的 Bash 區塊。

**三格判準**：

| 現場 | 行為 | 理由 |
|---|---|---|
| 當前分支 = 預設分支 | 放行 | `git-workflow.md` 第 1 條要的就是這個 |
| 當前分支 ≠ 預設分支 **且** 有 in-flight agent | **持續擋** | 那是**狀態**，放行一次那個 agent 照樣被抽掉 |
| 當前分支 ≠ 預設分支，無 in-flight agent | **擋一次** | 它傳達的是資訊（基底會錯），講一次就該讓路 |

deny-once 的標記記的是**分支名**，換一條 topic 分支會再擋一次（新的現場）；
回到預設分支時順手清標記。

**額外放行的一格（測試釘住）**：指令自己帶了 start-point（`git checkout -b x main`）
且無 in-flight agent → 放行。那本來就是攔截訊息推薦的繞法之一，閘門不能反過來擋它。
有 in-flight agent 時仍擋——start-point 解決「基底錯了」，解決不了「HEAD 被搬走」。

**實作要點**：
- 指令切段一律走 `lib/cmd-segments.sh` 的 `cmd_segments`／`cmd_match`，**沒有任何子字串比對**。
  `git checkout <既有分支>`、`git switch <既有分支>`、`git checkout -- <file>`、
  `git checkout .`、heredoc 內文提到指令，全部不誤擋（各有一條測試）。
- 「預設分支」不寫死 `main`：`refs/remotes/origin/HEAD` → `init.defaultBranch`（且本地
  真的有那條分支）→ 本地有沒有 `main`／`master`。三層都問不出來 → **放行**。
- detached HEAD 放行（從那裡開分支通常正是在救回東西）、非 git repo 放行。
- 逃生門 `BRANCH_SWITCH_GATE=off`；`.suggest-mode=off` 由 `pre-tool-use.sh` 上游處理。

**接線位置**：`merge-gate` → **`branch-switch-gate`** → `merge-noff-gate` → `git-backup-gate`。
理由寫在接線處：merge-gate 管的「上一批工作卡在半空中」該先講完；另外兩道管
merge／reset／push／rebase，跟 checkout／switch 不會是同一段指令，純看命中的話順序無所謂——
真正會撞在一起的是 `git checkout -b x && git reset --hard HEAD~1` 這種串接，
那時該先講「這條分支根本不該在這裡開」，先收到「去打 backup tag」等於在指導一個
不該發生的操作怎麼做得更安全。

**刻意留下的兩個判斷不了**（寫進檔頭，其中第一個也寫進攔截訊息）：
1. subagent 自己打這條指令時，in-flight 計數**包含它自己**——PreToolUse 的 payload
   分不出誰在打。結論仍成立（subagent 在共用 checkout 裡換分支本來就該改用 worktree），
   但數字的歸屬不精確，訊息裡明講，不假裝閘門知道它不知道的事。
2. 第一格（站在預設分支）即使有 in-flight agent 也放行。嚴格說 HEAD 一樣會被搬走，
   但「從預設分支開新分支」是本模板的主流程，擋它等於擋掉正常開發。

### 🟡 Medium — `worktree.baseRef` 查證結果：**維持 `"head"`，不改**

**查了哪裡**（兩輪 WebSearch，互相印證）：
- [anthropics/claude-code #57148](https://github.com/anthropics/claude-code/issues/57148)
  （`worktree.baseRef` setting not documented）
- [anthropics/claude-code #60588](https://github.com/anthropics/claude-code/issues/60588)
  （EnterWorktree ignores `baseRef: "fresh"`，v2.1.144 的已知 bug）
- [anthropics/claude-code #35730](https://github.com/anthropics/claude-code/issues/35730)
  （Allow configuring default base branch for `--worktree`）
- [官方 worktrees 文件](https://code.claude.com/docs/en/worktrees)

**看到什麼**：v2.1.133 引入 `worktree.baseRef`，**只有兩個合法值**——
`"fresh"`（官方預設，從 `origin/<default>` 開）與 `"head"`（從本地 HEAD 開）。
**不吃分支名字串**：「指定基底分支」至今仍是 #35730 那個**開著的 feature request**。
官方文件確實沒寫這個設定（#57148 就是在反映這件事），所以模板現有那張表
（`worktree-orchestration` skill 第 75 行起）是目前查得到最完整的整理，且與查證結果一致。

**決定：不改。** 沒有「更合適的值」可選——只有二選一，而模板選 `"head"` 的理由
已經寫在 skill 裡且仍然成立：這裡的平行流程是 `/plan` 寫出 plan → `/task-next` 判定
可平行 → 開 worktree 派 agent，那份 plan 剛寫好、**絕對還沒 push**。改成 `"fresh"`
會讓 worktree 從遠端開 → plan 不在裡面 → 隔離的 agent 讀不到自己要實作什麼。
用一個靜默的「agent 自己發明範圍」換掉一個看得見的「基底多了幾個 commit」，是虧的。

**代價則補上去**（第 4 項）：`"head"` 的代價本來只隱含在表格裡，現在明寫。

### 🔴 High — `worktree.symlinkDirectories` 讓「隔離」在執行層失效

**事故（使用者實測，2026-09-17）**：兩條 worktree 平行開發、檔案完全不重疊，
但 `symlinkDirectories` 預設含 `.venv` → worktree 的 `backend/.venv` 是**指回主 checkout
的 symlink** → 該 venv 裡 editable install 的 `.pth` 指的是主 checkout 的 source。
結果 worktree 裡 `router.__file__` 指向主 checkout，agent 跑測試測到的是另一條線的
程式碼（對方當時正在做突變測試），**而且沒有任何錯誤訊息**。

**逐項驗證五個預設值**（結論：五項全移除，`"symlinkDirectories": []`）：

| 值 | 判定 | 理由 |
|---|---|---|
| `.venv` | **移除** | 已實測。`uv` workspace 成員預設 editable install，`.pth` 記的是絕對來源路徑 |
| `.next` `dist` `build` | **移除** | **建置產物是「這份 source 的輸出」**。共用等於 B 服務／測試 A 的產出，同一個病。而且它們是重新產生的東西，沒有「省下載」這個原意可言 |
| `node_modules` | **移除** | 扁平非 workspace 專案確實安全（省 300–500MB/worktree 是真的），但 npm／pnpm workspaces 下 `node_modules/<pkg>` 是指回 repo source 的 symlink，同一個病；`node_modules/.prisma` 這類從 schema 產生的 client 也是 |

**為什麼敢動這個預設值**（跟 `baseRef` 那項用同一個判準，結論相反是因為情況不同）：
`baseRef` 是二選一，兩個值各有靜默失敗的可能，所以維持現狀 + 補說明。
`symlinkDirectories` 不是——**空的預設值不可能造成錯誤結果**，只會多花磁碟與安裝時間
（可見、可回復）；非空的會在某些專案形態下造成靜默的錯誤結果。
模板不知道目標專案是不是 monorepo、用不用 editable install，**不該替它做這個假設**。
要開的人照 skill 的判準表自己開。

順帶解掉的一個已知 bug：
[#40259](https://github.com/anthropics/claude-code/issues/40259)
（設了 `symlinkDirectories` 會讓 worktree 自動清理靜默失敗，因為 `git worktree remove`
拒絕移除含未追蹤檔案的 worktree，而那些 symlink 就是未追蹤檔案）。
另有 [#40857](https://github.com/anthropics/claude-code/issues/40857)（寫入 symlink 檔案時
會用 atomic write 把 symlink 本身換成一般檔案）。

**連帶三處**：
- `worktree-orchestration` skill「環境準備」整段改寫成 `symlinkDirectories` 節（**唯一來源**）：
  判準表（可 symlink = 純快取／純下載產物；不可 = 任何記錄來源路徑的東西 + 建置產物）、
  偵測與修法（`test -L` → `unlink` → `uv sync --all-packages`）、
  兩個容易做錯的細節（`rm -rf <路徑>/` 帶斜線會沿 symlink 刪掉主 checkout 那一份；
  只跑 `uv sync` 會修剪掉 workspace 成員）、驗收條件（不帶 `PYTHONPATH` 也載得對）。
  反模式清單加一條。
- `pre-agent-gate.sh` **只改檔頭**（程式行為不動）：原本「帶了 isolation → 改不到別人，
  直接放行」那句補上「只成立在檔案層」，點名這是繼寫撞寫、讀撞寫之後的**第三類：執行撞執行**，
  並寫明**為什麼刻意不做成閘門**——派工當下 worktree 還沒建，沒有東西可檢查；
  能檢查的時機要知道專案用不用 editable install／是不是 workspace，閘門問不出來；
  而誤擋的正是「帶 `isolation` 的派工」，那是我們花三課在推廣的做法。
  這一格由**設定預設值**（機器層、零判斷、不需要被想起來）負責。
- `rules/agent-orchestration.md`「安全平行」補一條（3 行）：那節原本的結論是
  「掃描類 agent 要平行**只能靠 worktree 隔離**」——現在那句話有前提了。
  只寫「隔離只到檔案層」+ 指回 skill，不重述判準。

**learned：新寫一篇**，不是擴充既有的
`2026-09-16-concurrent-read-write-not-file-overlap.md`。理由：
兩者的**強制者不同**（那篇是 `pre-agent-gate.sh` 的攔截訊息，這篇是設定預設值）、
**觸發時機不同**（派工當下 vs 建 worktree 時）、**可帶走的通則也不同**
（那篇是「檢查放行條件會不會恆為真」，這篇是「隔離要問到底是哪一層」）。
併進去會讓那篇的通則失焦。新檔：
`.claude/context/learned/2026-09-17-worktree-isolation-stops-at-the-file-layer.md`，
兩篇互相 link，並在新篇明寫「那一課的結論是『只能靠 worktree 隔離』，本課補的正是
那個結論的前提條件」。

### 測試沙箱的一個坑（順手釘住）

沙箱的初始分支名取決於跑測試那台機器的 `init.defaultBranch`（可能是 `master`）。
本閘門的判準正是「當前分支 == 預設分支嗎」，所以分支名必須是確定的——
新區塊開頭先 `git branch -M main` 釘住。其他區塊都不依賴分支名（它們只是把 `main`
當字串寫進指令），改名不影響。這條不釘的話在 CI 上會是隨機紅燈。
