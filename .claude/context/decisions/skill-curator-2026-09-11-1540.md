## 發現

### 🟡 Medium — 我自己寫的程式碼裡的 bug（由新測試抓到）

`grep -c` 在**數到 0 時會印出 "0" 並回傳 1**。我第一版寫成：

```bash
DIRTY_N=$(printf '%s\n' "$PORCELAIN" | grep -c '[^[:space:]]' 2>/dev/null || echo x)
```

於是乾淨的工作區拿到 `"0\nx"` → 非數字 → 判成「算不出來」→ **乾淨的工作區永遠不會
推薦 worktree**。手動 smoke test 一度「通過」，是因為舊版 `|| echo 0` 產生的 `"0\n0"`
讓 `[ ... -gt 0 ]` 報錯、掉進 `GIT_DIRTY=no` 這條**錯誤路徑上的正確答案**。
新加的「工作區乾淨 → 推薦帶隔離」那條直接打紅，才逼出真正的原因。
已移除 fallback（計數一律會印出來，command substitution 的結束碼在這裡無所謂）。

**這是這次最有價值的一件事**：三條測試不是同義反覆，它們有判別力。

### 🟡 Medium — 測試沙箱不能直接當 git repo

前面的區塊在共用 `$SANDBOX` 底下留了巢狀 git repo（`git-backup` 那組的
`emptyrepo` 等），`git add -A` 清不乾淨 → 「乾淨」那條假失敗（實得「有 3 個未 commit」）。
改成這三條自己開一個獨立 root（`$SANDBOX/pg-reco`），順便不必在結束時清
`$SANDBOX/.git`——那個清理動作本身就是個容易漏的隱性契約。

### 🟢 Low / Info — 兩個刻意的判斷

- **`plans/` 整個不存在時留 `unknown`，不當成「沒有 plan」。** 那種專案根本沒在用
  plan，說「你沒有任何帶 `files:` 的 plan」是拿模板的慣例去指責它。
  兩個檢查各自獨立，所以這種情況下推薦仍可能由「工作區乾不乾淨」給出
  （它的理由不涉及 plan）。**這是對「plans/ 不存在 → 安靜退回」的一種讀法**——
  若你要的是「plan 檢查失敗就整條推薦都不給」，講一句我改（一行 if）。
- **`git status` 數不出來時留 `unknown`，絕不退回 `"no"`。** 退回 `no` 會變成宣稱
  「工作區乾淨」並推薦 worktree——那是唯一一種會**主動誤導**的失敗方式。
  其餘失敗（沒 git、非 repo、status 非零）都只是少一行推薦。

## 遵守的限制

| 限制 | 實際做法 |
|---|---|
| 不動三個選項的文字與順序 | 一個字沒動；推薦加在前面、限制說明加在後面，選項段落原封不動 |
| 不加新檢查項 | 就 `git status` 與 `plans/` 兩項 |
| 不碰放行路徑 | 整段推薦邏輯在最後一個 `exit 0` **之後**才開始。放行時不多跑任何 `git` 指令、無任何輸出（有回歸釘住「放行時空輸出」） |
| 不加設定或開關 | 沿用 `PARALLEL_AGENT_GATE=off` |
| 不順手重構 | 閘門其餘部分零改動 |
| 訊息不要變成一大段 | 推薦一行、限制說明一行 |
