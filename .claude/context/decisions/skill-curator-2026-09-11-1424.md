- 閘門邏輯一直是對的，錯的是它讀的帳：`agent_complete` 記在 `PostToolUse(Agent)`，
  而 Agent 工具是非同步的 → in-flight 恆為 0，**閘門從裝上去那天沒攔過任何一次**。
  已改為 `agent_start`@`PostToolUse` + `agent_complete`@`SubagentStop`，對應鍵 `agent_id`。
- 附帶刪除 2026-09-09 那段 `SELF_ID` 排除邏輯（成因消失），並在該份 learned 加註取代說明。
- 243 → **256 案例全綠**；新增的 13 條一律走真的 `agent-monitor.sh`，不造假 JSONL。
  **行為驗證（真實 session 收到 `SubagentStop`）未由我實跑**，見「未驗證的部分」。

## 發現

### 🔴 Critical / High

- `.claude/hooks/agent-monitor.sh` — `agent_complete` 由 `PostToolUse(Agent)` 寫，
  而該事件只代表派工返回（實測 2 秒 vs agent 實跑 44 分鐘）→ 每筆 start 在 2 秒內被
  自己的 complete 沖銷，`pre-agent-gate.sh` 的 in-flight 恆為 0。
  **已修**：完成改由 `SubagentStop` 寫、`agent_start` 移到 `PostToolUse`（`agentId`
  只在 tool response 裡）、對應鍵 `tool_use_id` → `agent_id`。
- 同一個 bug 的**可觀測性**問題：閘門只在攔截時寫 `hooks.log`，沒攔截就什麼都不留，
  所以「壞掉」和「沒事」長得一模一樣。這是它活這麼久的直接原因。
  **未改**（加 log 會在每次委派留噪音）；改用測試覆蓋補上，見度量。

### 🟡 Medium

- `.claude/hooks/agent-monitor.sh` — Git Bash 下 `jq ... | @tsv` 輸出 CRLF，
  **最後一個欄位夾帶 `\r`**。以前最後一欄是 `TOOL_USE_ID`、只用於截斷顯示所以看不出來；
  新增的 `AGENT_ID` 要拿來判空與比對，`\r` 會讓同步／非同步分支永遠走錯邊。
  第一次 smoke test 就撞到（`aid:"ag001\r"`），已加 `tr -d '\r'` 並註明原因。
- `.claude/hooks/README.md` — `pre-agent-gate.sh` **完全沒被記載**（檔案結構樹與
  各 hook 功能表都缺）。模板唯一的兩支 PreToolUse 閘門之一沒有文件。已補。
- 舊格式紀錄（只有 `tool_use_id`、無 `agent_id`）在換鍵後會全部歸到同一個 null 鍵下
  互相沖銷。閘門已明確 `select(. != "")` 忽略之，並加一條回歸釘住。

### 🟢 Low / Info

- **`post-agent-report.sh` 不受這個 bug 影響，刻意沒動**（主模型要求我判斷後回報）。
  它 `:82` 就在偵測 `async_launched`／`isAsync`，命中就只記期望到
  `.report-expectations.jsonl`，由 `lib/check-report-expectations.sh` 在後續對話邊界
  重查並注入——**它一開始就知道 PostToolUse 不是完成**。它的職責是報告落點稽核，
  與 in-flight 計數無關。可考慮的改進是改用 `SubagentStop` 當更準的重查時機，
  但現行機制有效，不在本次範圍。
- 同一則訊息連派多個時擋在第幾個：`dividend-rights` 的 3-agent 批次實測，
  **第 1 個的 PostToolUse 早於第 2 個的 PreToolUse 5 秒 → 第 2 個會被擋**；
  但第 3 個的 PreToolUse 早於第 2 個的 PostToolUse，可見這條鏈不是嚴格交錯。
  不影響設計（deny-once 本來就是一批只擋一次），已寫進閘門檔頭。
- 任務 B：新增那一列刻意只寫 **go/no-go 與後果**，前置動作留在「派工前務必做的一件事」，
  兩處互相指向而不重複。該節另補一句區分：共用定義漏了會變成**看得見的合併衝突**、
  baseline 漏了 agent **只會安靜重建一份**——後者才是 `dividend-rights` 那次的形狀。

## 未驗證的部分（**這段不要跳過**）

- **接線正確 ≠ 行為已驗證。** 我驗到的是：`settings.json` 的 `SubagentStop` 接線合法、
  `agent-monitor.sh` 對實測欄位形狀的 payload 產生正確帳目、閘門對該帳目做出正確裁決。
  **我沒有在真實 session 裡觀察到一次 `SubagentStop` 觸發**——那需要派一個 subagent
  並等它結束，而我自己就是 subagent。`SubagentStop` 會觸發、payload 欄位、
  `agent_id` 與 `agentId` 一致、hook 熱載入，這四件事全部**沿用主模型的探針實測結果**。
- 最快的確認方式：下次派任何 subagent，等它結束後跑
  `jq -rc 'select(.event=="agent_complete")|{ts:.timestamp,aid:.agent_id}' .claude/logs/agent-activity.jsonl | tail -3`
  ——出現帶 `agent_id` 的 complete 就是通了。**再派第二個同時跑，應該要被擋一次。**
- 未跑 `.claude/tests/skill-compliance/`：本次沒有改任何注入內容或給模型讀的規則
  （任務 B 是 skill 內文補一列，不涉及喚起路徑），壓力測試對這次的改動沒有判別力。
