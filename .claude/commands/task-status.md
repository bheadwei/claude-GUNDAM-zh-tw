# 專案狀態

## 功能

顯示 WBS 任務清單的完整狀態，包含進度、阻塞項和下一步建議。

## 資料來源

**必須** 從 `.claude/taskmaster-data/wbs.md` 讀取 WBS 資料。

如果檔案不存在，提示使用者先執行 `/task-init` 初始化專案。

## 流程

1. 讀取 `.claude/taskmaster-data/wbs.md`
2. **沒有 `## 現況` 區 → 舊格式**，先走下方「舊格式轉換」節的提議（可拒絕，拒絕就照舊顯示）
3. 解析各里程碑節的任務表，統計各狀態數量
4. **讀取** `.claude/taskmaster-data/plans/INDEX.md`（若存在），建立 `<task-id> → plan 進度` 映射
5. 顯示統計和任務清單（含 plan 進度欄位）
6. 如有任務狀態變更，**立即更新** wbs.md 並重算「現況」區

> 版面與「現況」的重算規則：`.claude/templates/wbs.template.md`（唯一來源）。

## 輸出格式

```
專案狀態:
  總任務: [N] 個
  待處理: [X] 個
  進行中: [X] 個
  已完成: [X] 個
  阻塞:   [X] 個
  進度:   [=====-----] X%

任務清單:
  [完成] 1.1 專案初始化                          Plan: —
  [完成] 1.2 需求分析                            Plan: —
  [進行] 2.1 架構設計           ← 當前            Plan: 🔄 2/4
  [待處理] 2.2 API 設計                          Plan: ⚪ 尚無
  [待處理] 3.1 核心功能開發                       Plan: ⚪ 尚無
  ...

下一步建議: /task-next
```

> 本指令**不做模板合規檢查**（那是 `/template-check` 的職責）。
> 只在需要時於「下一步建議」附帶提示。

## WBS 歸檔（本節是歸檔規則的唯一來源）

專案越做越大時 `wbs.md` 會無限膨脹。解法與 `plans/archive/`、`context/_archive/`
同構：**以里程碑為邊界歸檔**，讓 `wbs.md` 的長度跟「還活著的任務」掛鉤，
而不是跟專案總量掛鉤。

### 檔案

```
.claude/taskmaster-data/
├── wbs.md            # 只留：活躍里程碑的任務 + 「現況」裡一列已歸檔摘要
└── wbs-archive.md    # 已完成里程碑的完整任務列（多一個「實際」欄）
```

### 觸發時機（提議，不強制）

用 `AskUserQuestion` 詢問，使用者可拒絕：

| 時機 | 誰觸發 |
|---|---|
| 某個里程碑的所有任務都 ✅ | `/verify` 標記最後一個任務完成時 |
| `wbs.md` 任務列超過 **40 行** | `/task-status` 顯示完畢後 |
| 使用者主動要求 | `/task-status` 對話中提出 |

### 歸檔程序

1. 確認該里程碑**所有**任務為 `✅`（任何完成日）或 `⏭️ 跳過`（有任何 ⏳/🔄/🚫 就不能歸檔）
2. 把該里程碑節**整段搬到** `wbs-archive.md`（不存在則建立），
   版面見 `.claude/templates/wbs.template.md` 第 5 節（與 wbs.md 同欄位，多一個「實際」欄；
   節標題帶起訖日、項數、預估／實際總計）。
   有 `timelog.jsonl` 資料時**一併寫入「實際」欄**——歸檔後仍要能回顧估準不準。
   計畫連結改指 `plans/archive/…`（`/verify` 歸檔 plan 時應已改好，這裡再核一次）。
   「負責」欄原樣帶過去。新節用範本第 5 節的**新表頭**；`wbs-archive.md` 裡既有的舊節
   （加入負責欄之前歸檔的）**原樣保留、不回填、不改表頭**——每節自帶表頭，欄位以該節表頭為準

3. `wbs.md` 移除該里程碑節，**其他任務的編號一律不變**
4. 重算「現況」區：該里程碑併進已歸檔那一列（例：`| M1–M10 | 已歸檔 86 項 | ✅ 完成 | — |`），
   N 只算 ✅、不含 ⏭️；總進度的分子與分母都含這 N 項（算法見範本第 3 節）
5. 更新「最後更新」日期

### 編號不重用（CRITICAL）

歸檔後 `1.x`、`2.x` 這些編號**永久保留給已歸檔任務**。
`/task-add` 追加新任務時必須**同時掃 `wbs.md` 與 `wbs-archive.md`** 才能決定下一個可用編號，
否則會撞號、讓 `timelog.jsonl` 與 plan 檔的對應錯亂。

### 狀態顯示

歸檔後 `/task-status` 的輸出改為：

```
專案狀態:
  活躍任務: 8 個（待處理 5 ・ 進行中 1 ・ 阻塞 2）
  已歸檔:   34 個（M1、M2）
  總進度:   [========--] 81%   ← 分母含已歸檔

里程碑:
  ✅ M1: MVP        12 個 / 預估 24.5h / 實際 27h（已歸檔）
  ✅ M2: 通知系統    22 個 / 預估 41h   / 實際 38h（已歸檔）
  🔄 M3: 報表        8 個 / 預估 16h（進行中）
```

`--detailed` 時才展開已歸檔內容（讀 `wbs-archive.md`；各節欄位不同，**依該節表頭取欄**）。

### 其他指令的配合

| 指令 | 要做什麼 |
|---|---|
| `/time-log --by-task` | 找不到任務時**再查一次 `wbs-archive.md`**，不要顯示為「未分類」 |
| `/task-add` | 掃兩個檔決定新編號（見上） |
| `/task-next` | 只讀 `wbs.md`（歸檔的任務都完成了，不會是候選） |

### Plan 進度符號

- `🔄 N/M`：進行中，已完成 N 個階段 / 共 M 階段
- `⏳ 0/M`：計畫已建立但尚未開始
- `✅ 已歸檔`：任務完成後 plan 移至 `plans/archive/`
- `⚪ 尚無`：WBS 任務無對應 plan 檔
- `—`：已完成任務且無歷史 plan 記錄

## 舊格式轉換（既有專案的一次性遷移）

**偵測**：`wbs.md` 沒有 `## 現況` 區。舊格式有兩代——欄位是 `… | 預估 | Plan | 備註 |`，
或更舊的連 `Plan` 欄都沒有（plan 連結散在「備註」或根本沒有）。兩代都走這一節。

命中就在**顯示狀態之前**用 `AskUserQuestion` 提議（可拒絕）：

> 這份 WBS 是舊版面（沒有「現況」區，狀態／備註格裡塞了長內容）。
> 新版面每格一行、依里程碑分節，長內容搬到 plan／報告／帳本，WBS 只留連結。要轉換嗎？

- **轉換**（Recommended）— 走下方程序，寫入前先給預覽
- **先看預覽再決定** — 跑到步驟 6 為止，不寫檔
- **不要，維持舊版面** — 本 session 不再提

目標版面見 `.claude/templates/wbs.template.md`（唯一來源）；長內容的去處是它的**第 4 節**。

### 轉換程序

**原則：不能丟資料。** 搬不確定的寧可問，不要自己判斷刪掉。

1. **先保住原檔**：`wbs.md` 已進版控且無未提交變更 → 靠 git 即可；
   否則先複製成 `wbs.pre-migration.md`，轉換完成並經使用者確認後再刪
2. **逐列拆格子**。每一列的「狀態」「備註」（以及任何超過一行的格子）切成片段，依範本第 4 節分類：

   | 片段 | 去處 | 原列留下 |
   |---|---|---|
   | 狀態符號＋完成日 | 留在狀態欄 | `✅ 09-23` |
   | `[計畫](…)` 連結（舊 `Plan` 欄或備註裡的） | 連結欄 | 原連結 |
   | 驗證數據、執行結果 | 有 plan → 追加到該 plan 的「驗收標準（整體）」；無 plan → 遷移紀錄 | `[報告](…)` 或不留 |
   | 進度、派工、commit SHA | 有帳本 → 追加到帳本；無 → 遷移紀錄 | `[帳本](…)` 或不留 |
   | 帶給下一任務的疑慮 | **下一任務**的 plan「風險與緩解」；下一任務還沒有 plan → 遷移紀錄，並在報告中列出待建 plan 時要搬的項目 | 不留 |
   | 選型與理由 | `context/decisions/`（新 ADR 或追加既有） | 必要時 `[ADR](…)` |
   | 阻塞原因 | 「風險與阻塞」表新增一列 `R<n>` | 狀態 `🚫 阻塞` ＋ 連結欄 `R<n>` |
   | 任務等級（critical 等） | 有 plan → frontmatter `mode:`；無 → 遷移紀錄 | 不留 |
   | 歸不了類的 | **列出來問使用者**（見步驟 5） | — |

   搬進 plan／帳本的段落尾端加 `（自 WBS 搬入 YYYY-MM-DD）`，讓日後知道來源。
3. **遷移紀錄**：每個被搬動的格子的**原文全文**（不是摘要）依任務編號寫進
   `.claude/context/decisions/wbs-migration-YYYY-MM-DD.md`。這是保底——
   就算步驟 2 分類錯了，原文仍在，可以再搬一次
4. **補連結欄**：掃 `plans/*.md` 與 `plans/archive/*.md` 的 frontmatter `wbs_task`，
   有對應的填 `[計畫](plans/<檔名>.md)`（已歸檔填 `plans/archive/…`）；
   `wbs_task: "none"` 的 ad-hoc plan 跳過；`wbs_task` 在 WBS 找不到任務的 → **不要猜**，列出來。
   **「負責」欄一律填 `—`**——不從備註或 commit 作者推人名（指派是使用者的決定）
5. **分節**：依舊「里程碑」表的「包含任務」把任務分進 `## M<n> <名稱>` 節；
   沒被任何里程碑涵蓋的任務 → 列出來問要放哪（一次一題，可提議「全部放一個新里程碑」當 Recommended）。
   歸不了類的片段也在這一步一併問：**把清單貼出來**，選項為
   「全部只留在遷移紀錄（Recommended）」「逐條決定去處」
6. **預覽**：給使用者看 ①新 `wbs.md` 全文 ②每個片段搬到哪個檔 ③遷移紀錄路徑
7. 確認後寫入：新 `wbs.md`（含重算的「現況」區）、各 plan／帳本／ADR 的追加段落、遷移紀錄

轉換只做一次。之後的寫入由 `post-write.sh` 檢查格子長度——超過約 40 字會提醒該搬去哪
（只提醒，不擋；`WBS_CELL_CHECK=off` 可關）。

## WBS／plans 進版控（既有專案的一次性遷移）

較舊的專案沿用舊版 `.gitignore`，那份把 `.claude/taskmaster-data/` **整個**忽略掉，
所以 `wbs.md` 與 `plans/` 從來沒進版控。新版改成細分規則——只忽略執行時短命狀態。

**偵測方式**：專案是 git repo 且 `wbs.md` 存在，但 `git ls-files .claude/taskmaster-data`
回傳空的。命中就在顯示狀態後用 `AskUserQuestion` 提議（可拒絕）：

> 這個專案的 WBS 與 plans 還沒進版控（舊版 `.gitignore` 把整個 `taskmaster-data/` 忽略了）。
> 進版控的好處：規格與計畫可 review／可追溯、跨機器同步、**worktree 平行開發才拿得到 plan**。
> 要現在納入嗎？

### 遷移程序

1. **外科式修改專案的 `.gitignore`**（`update-template` **不會**同步它——
   專案會自己加建置產物等規則，而根目錄檔案不在 update-template 的備份範圍內，
   覆寫等於無備份的破壞）：

   - **刪掉**這兩行（若存在）：`.claude/taskmaster-data/`、`.claude/sessions/`
   - **加入**模板 `.gitignore` 的「執行時短命狀態」整段（11 條 `.claude/taskmaster-data/.*`
     加上 `.claude/worktrees/`）—— 直接從模板那份複製過去
   - 專案自己原有的規則**一條都不要動**

2. `git add .claude/taskmaster-data/` —— 細分規則會自動擋掉短命狀態檔
3. **`git status` 給使用者看清單再 commit**，不要自動 commit
4. **提醒敏感資料**：`plans/` 與 `wbs.md` 可能含客戶名稱、內部系統名。
   進了 git 歷史刪不掉——檢查清單見 `.claude/commands/save-session.md`

`sessions/` 與 `qa-history/` 同理（舊版也把 `sessions/` 忽略了）。它們**更容易夾帶敏感資料**
（記錄的是對話內容），所以分開問一次，別跟 WBS 混在同一個 commit。

## 更新任務狀態

當使用者告知某任務已完成或有進展時：
1. 讀取 `.claude/taskmaster-data/wbs.md`
2. 更新對應任務的狀態欄位——**只改符號與日期**（`✅ 09-23`、`🚫 阻塞`）。
   使用者附帶的說明（「token 生成還沒做」「卡在客戶主機」）依範本第 4 節放到 plan／帳本／風險表，不要寫進格子
3. 重算「現況」區與總進度，更新「最後更新」日期
4. 寫回檔案

## 時間追蹤整合

顯示狀態時，如果 `.claude/taskmaster-data/timelog.jsonl` 存在，額外顯示：

1. 在任務清單中，對有時間記錄的任務顯示「實際時間」欄位
2. 與 WBS 預估時間對比，顯示差異
3. 顯示當前正在追蹤的任務（讀取 `.current-task`）

輸出範例：
```
任務清單:
  [完成] 1.1 專案初始化          預估 0.5h │ 實際 0h25m ✅
  [完成] 1.2 需求分析            預估 2h   │ 實際 1h50m ✅
  [進行] 2.1 架構設計     ⏱️     預估 2h   │ 已花 1h15m（進行中）
  [待處理] 2.2 API 設計          預估 1h   │ --
```

## 使用方式

```
/task-status              # 簡要狀態（含 plan 進度）
/task-status --detailed   # 含每個任務詳情（展開 plan 階段）
/task-status --metrics    # 含效能指標和時間追蹤
```
