# 專案狀態

## 功能

顯示 WBS 任務清單的完整狀態，包含進度、阻塞項和下一步建議。

## 資料來源

**必須** 從 `.claude/taskmaster-data/wbs.md` 讀取 WBS 資料。

如果檔案不存在，提示使用者先執行 `/task-init` 初始化專案。

## 流程

1. 讀取 `.claude/taskmaster-data/wbs.md`
2. 解析任務清單表格，統計各狀態數量
3. **讀取** `.claude/taskmaster-data/plans/INDEX.md`（若存在），建立 `<task-id> → plan 進度` 映射
4. 顯示統計和任務清單（含 plan 進度欄位）
5. 如有任務狀態變更，**立即更新** wbs.md 檔案

## 輸出格式

```
專案狀態:
  總任務: [N] 個
  待處理: [X] 個
  進行中: [X] 個
  已完成: [X] 個
  阻塞:   [X] 個
  進度:   [=====-----] X%

任務清單:
  [完成] 1.1 專案初始化                          Plan: —
  [完成] 1.2 需求分析                            Plan: —
  [進行] 2.1 架構設計           ← 當前            Plan: 🔄 2/4
  [待處理] 2.2 API 設計                          Plan: ⚪ 尚無
  [待處理] 3.1 核心功能開發                       Plan: ⚪ 尚無
  ...

下一步建議: /task-next
```

> 本指令**不做模板合規檢查**（那是 `/template-check` 的職責）。
> 只在需要時於「下一步建議」附帶提示。

## WBS 歸檔（本節是歸檔規則的唯一來源）

專案越做越大時 `wbs.md` 會無限膨脹。解法與 `plans/archive/`、`context/_archive/`
同構：**以里程碑為邊界歸檔**，讓 `wbs.md` 的長度跟「還活著的任務」掛鉤，
而不是跟專案總量掛鉤。

### 檔案

```
.claude/taskmaster-data/
├── wbs.md            # 只留：活躍任務 + 里程碑摘要表
└── wbs-archive.md    # 已完成里程碑的完整任務列（含歷史預估/實際）
```

### 觸發時機（提議，不強制）

用 `AskUserQuestion` 詢問，使用者可拒絕：

| 時機 | 誰觸發 |
|---|---|
| 某個里程碑的所有任務都 ✅ | `/verify` 標記最後一個任務完成時 |
| `wbs.md` 任務列超過 **40 行** | `/task-status` 顯示完畢後 |
| 使用者主動要求 | `/task-status` 對話中提出 |

### 歸檔程序

1. 確認該里程碑**所有**任務為 `✅ 完成` 或 `⏭️ 跳過`（有任何 ⏳/🔄/🚫 就不能歸檔）
2. 把這些任務列**整段搬到** `wbs-archive.md`（不存在則建立），依里程碑分節：

   ```markdown
   ## M1: MVP（2026-06-01 ~ 2026-08-10）

   | # | 任務 | 狀態 | 優先級 | 依賴 | 預估 | 實際 | 備註 |
   |---|------|------|--------|------|------|------|------|
   | 1.1 | 專案初始化 | ✅ | 高 | - | 0.5h | 0h25m | |
   ```

   有 `timelog.jsonl` 資料時**一併寫入「實際」欄**——歸檔後仍要能回顧估準不準。

3. `wbs.md` 的里程碑表把該列改為已歸檔並補上統計：

   ```markdown
   | M1: MVP | 2026-08-10 | 12 個任務 / 預估 24.5h / 實際 27h | ✅ 已歸檔 |
   ```

4. `wbs.md` 的任務清單移除這些列，**其他任務的編號一律不變**
5. 更新「最後更新」日期

### 編號不重用（CRITICAL）

歸檔後 `1.x`、`2.x` 這些編號**永久保留給已歸檔任務**。
`/task-add` 追加新任務時必須**同時掃 `wbs.md` 與 `wbs-archive.md`** 才能決定下一個可用編號，
否則會撞號、讓 `timelog.jsonl` 與 plan 檔的對應錯亂。

### 狀態顯示

歸檔後 `/task-status` 的輸出改為：

```
專案狀態:
  活躍任務: 8 個（待處理 5 ・ 進行中 1 ・ 阻塞 2）
  已歸檔:   34 個（M1、M2）
  總進度:   [========--] 81%   ← 分母含已歸檔

里程碑:
  ✅ M1: MVP        12 個 / 預估 24.5h / 實際 27h（已歸檔）
  ✅ M2: 通知系統    22 個 / 預估 41h   / 實際 38h（已歸檔）
  🔄 M3: 報表        8 個 / 預估 16h（進行中）
```

`--detailed` 時才展開已歸檔內容（讀 `wbs-archive.md`）。

### 其他指令的配合

| 指令 | 要做什麼 |
|---|---|
| `/time-log --by-task` | 找不到任務時**再查一次 `wbs-archive.md`**，不要顯示為「未分類」 |
| `/task-add` | 掃兩個檔決定新編號（見上） |
| `/task-next` | 只讀 `wbs.md`（歸檔的任務都完成了，不會是候選） |

### Plan 進度符號

- `🔄 N/M`：進行中，已完成 N 個階段 / 共 M 階段
- `⏳ 0/M`：計畫已建立但尚未開始
- `✅ 已歸檔`：任務完成後 plan 移至 `plans/archive/`
- `⚪ 尚無`：WBS 任務無對應 plan 檔
- `—`：已完成任務且無歷史 plan 記錄

## Plan 欄回填（既有專案的一次性遷移）

較舊的專案 `wbs.md` 表頭沒有 `Plan` 欄，plan 連結可能散在「備註」欄或根本沒有。
**若偵測到表頭缺 `Plan` 欄**，在顯示狀態後用 `AskUserQuestion` 提議回填（可拒絕）：

> 這個專案的 WBS 還沒有 `Plan` 欄。掃到 N 份 plan 可對應到任務，要回填嗎？

### 回填程序

1. 掃 `plans/*.md` 與 `plans/archive/*.md`，讀每份的 frontmatter `wbs_task`
2. `wbs_task: "none"` 的 ad-hoc plan **跳過**（不屬於任何 WBS 任務）
3. 在表頭「預估」與「備註」之間插入 `Plan` 欄，所有既有列同步補格
4. 逐列填入：
   - 有對應 plan → `[計畫](plans/<檔名>.md)`
   - 已歸檔 → `[計畫](plans/archive/<檔名>.md)`
   - 其餘 → `-`
5. **若「備註」欄原本就有 `[計畫](...)` 連結**（舊規範放那裡）→ 移到 `Plan` 欄，備註只留其他文字
6. `wbs_task` 在 WBS 找不到對應任務的 plan → **不要猜**，列出來讓使用者決定
   （通常是任務編號改過，或該任務已被刪除）

回填只做一次。之後 `Plan` 欄由 `/plan` 建立時填入、`/verify` 歸檔時改指 `archive/`
——規範見 `plan-format` skill 的「與 WBS 的雙向同步」。

## 更新任務狀態

當使用者告知某任務已完成或有進展時：
1. 讀取 `.claude/taskmaster-data/wbs.md`
2. 更新對應任務的狀態欄位
3. 更新「最後更新」日期
4. 寫回檔案

## 時間追蹤整合

顯示狀態時，如果 `.claude/taskmaster-data/timelog.jsonl` 存在，額外顯示：

1. 在任務清單中，對有時間記錄的任務顯示「實際時間」欄位
2. 與 WBS 預估時間對比，顯示差異
3. 顯示當前正在追蹤的任務（讀取 `.current-task`）

輸出範例：
```
任務清單:
  [完成] 1.1 專案初始化          預估 0.5h │ 實際 0h25m ✅
  [完成] 1.2 需求分析            預估 2h   │ 實際 1h50m ✅
  [進行] 2.1 架構設計     ⏱️     預估 2h   │ 已花 1h15m（進行中）
  [待處理] 2.2 API 設計          預估 1h   │ --
```

## 使用方式

```
/task-status              # 簡要狀態（含 plan 進度）
/task-status --detailed   # 含每個任務詳情（展開 plan 階段）
/task-status --metrics    # 含效能指標和時間追蹤
```
