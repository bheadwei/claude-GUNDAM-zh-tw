# 新增任務到 WBS

**本質是「針對單一功能的迷你 `/task-init`」**——同樣的拆解邏輯，但 append 而不是重建。

> **CR 累積提醒**：本指令加進來的任務若屬客戶 CR（而非原本 PRD 就有的功能），
> 它通常**不會**回寫進 PRD——那是「程式做了但規格沒說」的來源。
> 累積約 5 個以上時，載入 `spec-convergence` skill 跑一次 A+B 檢查，
> 把該回寫 PRD 的部分補上。`/verify` 在里程碑完成時也會自動提議。


## 為什麼需要它

`/task-init` 只在專案開頭跑一次。之後想加功能時，如果直接跳去 `/plan`，
**WBS 那一行永遠不會被建立**，plan 就被迫兼差當 backlog——這正是「plan 感覺很像 WBS」的成因。

兩者的分工是：

| | WBS | Plan |
|---|---|---|
| 回答 | 「還有什麼要做」 | 「這件事怎麼做」 |
| 顆粒 | 一個任務**一行** | 一個任務**一份檔** |

`/task-add` 補的是那一行。plan 照舊只在達門檻時才產。

## 前置

`.claude/taskmaster-data/wbs.md` 必須存在。不存在 → 提示先執行 `/task-init`，停止。

## 執行流程

### 互動原則（CRITICAL）

遵守 `.claude/rules/interactive-qa.md`：用 `AskUserQuestion` 一次一題；
問答在記憶中收集，結束後**一次性** Write 到
`.claude/qa-history/YYYY-MM-DD-HHMMSS-task-add.md`。

### 步驟 1：讀取現況（自動，不問使用者）

1. 讀 `wbs.md`，理解：編號體系（`1.x` / `2.x` …）、既有里程碑節、各任務狀態
2. **同時讀 `wbs-archive.md`（若存在）** —— 歸檔的編號永久保留、**不可重用**。
   決定新編號時必須把兩個檔案的編號都算進去，否則會撞號並讓
   `timelog.jsonl` 與 plan 檔的對應錯亂。（歸檔規則見 `/task-status` 的「WBS 歸檔」節）
   `wbs-archive.md` 各節的欄位數可能不同（加入負責欄之前歸檔的節少一欄）——
   **依各節表頭找 `#` 欄**，不要假設固定欄位位置
3. 讀 `.claude/taskmaster-data/project.json` 取得專案模式（demo/mvp/full）與語言
4. 掃 `plans/INDEX.md`，知道哪些任務已有計畫

### 步驟 2：問要加什麼

用 `AskUserQuestion` 問**一題**：

> **題目：** 要新增什麼功能？（直接輸入描述即可）

**不要**設「自訂」選項再追問——直接讓使用者在回答框打字。
可提供 2-3 個依專案上下文推測的選項當提示，但說明中要寫「或直接輸入」。

### 步驟 3：拆解與定位（自動分析，產出預覽）

依描述判斷這是**一個任務還是數個**：

- 單一、清楚、< 4h → 1 行
- 含多個技術層次（資料層 / API / UI）→ 拆成數行，彼此建立依賴

決定每一行的：

| 欄位 | 怎麼決定 |
|---|---|
| **編號** | 屬於既有分組 → 該組下一個可用號（如 `2.4`）；是全新領域 → 開新組（如 `5.1`） |
| **里程碑** | 放進哪個既有里程碑節，或開新里程碑（編號組與里程碑不必一一對應） |
| **依賴** | 掃 WBS 找出必須先完成的既有任務；同批新任務之間也要標 |
| **預估** | 參考 WBS 既有任務的預估尺度，保持一致 |
| **優先級** | 依是否阻塞其他任務、是否為使用者明確要的當前重點 |
| **建議模式** | 依 `rules/task-mode.md` 啟發式（觸及 auth/金流/migration → critical） |

### 步驟 4：預覽 + 確認

呈現將要追加的內容，**明確標出新增的行**：

```
將追加到 WBS：

| # | 任務 | 優先級 | 依賴 | 預估 | 建議模式 |
|---|------|--------|------|------|----------|
| 4.1 | 通知資料表與 schema | 高 | 2.3 ✅ | 1.5h | standard |
| 4.2 | 通知 API 端點 | 高 | 4.1 | 2h | standard |
| 4.3 | 通知中心 UI | 中 | 4.2 | 3h | standard |

放入里程碑：新增「M4 通知系統」
總計 +3 個任務、+6.5h
```

> 寫回 `wbs.md` 時，`狀態` 欄填 `⏳ 待處理`、`負責` 欄填 `—`（使用者在描述裡指名負責人時才填人名，
> 一個、小寫；不要自己推測）、`連結` 欄填 `—`（計畫還不存在，由後續 `/plan` 回填）。
> **欄位與版面的唯一來源是 `.claude/templates/wbs.template.md`**，勿在此重述。
> 建議模式**不寫進 WBS**（範本第 4 節：任務等級屬 plan frontmatter）——預覽給使用者看就好。

用 `AskUserQuestion` 問：

- **確認追加**（Recommended）
- **調整拆解** — 讓使用者說要怎麼改（合併/再拆/改依賴），回到步驟 3
- **只加一行就好** — 不拆解，整個功能當一個任務
- **取消**

### 步驟 5：寫回 WBS

1. 在 `wbs.md` 對應**里程碑節**插入新行；屬於新里程碑就新增一節 `## M<n> <名稱>`，
   並問一次目標日（範本第 3 節：目標日是現況表裡唯一不是算出來的欄位）
2. 依範本第 3 節**重算「現況」區與總進度**，更新檔頭的「最後更新」日期
3. **不動**既有任務的任何欄位

> `post-write.sh` 會自動記錄這次 WBS 變更到 `wbs-history.log`。

### 步驟 6：問要不要現在開始

用 `AskUserQuestion`：

- **現在就開始第一個**（Recommended）→ 目標固定為**新任務的第一個 id**（不重新跑 `/task-next` 的建議，
  否則可能被推薦成別的任務）。照 `/task-next` 的「選擇任務模式」與「狀態同步」兩節做（唯一來源）。
  該任務的依賴未全部 ✅ → 不開始，告知卡在哪幾個依賴，改問要不要先做那些
- **先規劃** → 對第一個新任務執行 `/plan <id>`。任務維持 `⏳ 待處理`（`/plan` 只寫計畫）；
  之後跑 `/tdd` 時會列出未開始的 plan 讓你選，選定才標進行中
- **先不動，之後再說** → 結束，提示可用 `/task-status` 查看

## 使用方式

```
/task-add
```

不接受參數，一律走互動流程（符合 `interactive-qa.md`；也避免誤加）。

## 何時會被自動提起

不用記這個指令也沒關係，三個地方會主動問你：

| 時機 | 誰問 |
|---|---|
| WBS 待辦清空時 | `/task-next` |
| ad-hoc plan 完成驗收時 | `/verify`（問要不要補登） |
| 你說「想加一個功能…」 | `user-prompt-submit.sh` 關鍵字提示 |

## 邊界情況

| 情境 | 處理 |
|---|---|
| `wbs.md` 不存在 | 提示先 `/task-init`，停止 |
| 描述太模糊（如「優化一下」） | 追問一題釐清具體要什麼，不要憑空拆解 |
| 新功能與既有任務重疊 | 指出重疊的任務編號，問是「取代」「合併」還是「確實是新的」 |
| 使用者想加的其實是 bug 修復 | 照樣加進 WBS（bug 也是任務），但預估與模式依 bug 規模判 |
| 追加後專案模式明顯不符（demo 卻加了 10 個任務） | 提示「規模已超過 demo，建議 `/docs-init --mvp` 補文件」，但不強制 |
