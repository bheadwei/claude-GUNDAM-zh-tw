# 技術決策記錄（ADR）

## 為什麼需要

`.claude/context/decisions/` 的職責寫著「**主 Agent** 技術決策記錄」，
但實際上只有 `architect` agent 會寫。**你我在對話中做的選型完全沒有留下**——
選了哪個函式庫、為什麼這樣切、哪個方案被否決過。

下個 session 不知道理由，就會重新爭論、或推翻一個其實有理由的決定。

## 什麼值得記

**要記**：

- 技術選型（用哪個函式庫/框架/服務，且**有評估過替代方案**）
- 架構切分（為什麼這樣分層、為什麼不拆微服務）
- 明確的取捨（選了效能犧牲可讀性、選了簡單犧牲彈性）
- **被否決的方案**——這比選中的更有價值，能防止下次重走死路
- 因外部限制而做的妥協（套件 bug、平台限制、時程）

**不要記**：

- 沒有替代方案的「決定」（只有一條路可走，那不是決策）
- 實作細節（那是程式碼與註解的事）
- 可逆的小選擇（變數命名、檔案位置）
- 需求本身（那是 PRD）

> 判準：**三個月後有人問「為什麼不用 X？」，你答得出來嗎？** 答不出來就該記。

## 執行流程

遵守 `.claude/rules/interactive-qa.md`：一次一題。

### 步驟 1：確認要記什麼

若 `$ARGUMENTS` 有內容 → 以此為主題。
否則用 `AskUserQuestion` 問：「要記錄什麼決策？」——**從當前對話中挑出 2-3 個候選**
當選項（你剛剛才討論過，不要讓使用者重打），並註明可直接輸入。

### 步驟 2：補齊四要素

決策記錄的價值全在這四項。缺哪個就問哪個（已在對話中講過的**不要重問**）：

1. **背景** — 什麼情況逼我們必須做這個選擇
2. **選了什麼**
3. **評估過哪些替代方案，為什麼否決**
4. **後果** — 得到什麼、犧牲什麼、什麼情況下該重新考慮

### 步驟 3：寫入

編號規則：`ADR-{YYYY-MM-DD}-{當日序號}-{kebab-標題}.md`
（掃 `context/decisions/` 現有檔案決定序號）

```markdown
# ADR-2026-08-10-001: 用 Zustand 而非 Redux 管理前端狀態

**日期：** 2026-08-10
**狀態：** 已接受
**決策者：** 主 Agent + 使用者

## 背景

<什麼情況逼我們做這個選擇。含當時的限制：時程、團隊熟悉度、既有技術棧>

## 決策

<選了什麼。一句話講完>

## 替代方案

| 方案 | 優點 | 否決理由 |
|---|---|---|
| Redux Toolkit | 生態成熟、devtools 強 | 樣板碼多，本專案狀態量不足以攤平成本 |
| Context + useReducer | 零依賴 | 跨元件更新會過度 re-render |

## 後果

**得到：** <好處>
**犧牲：** <代價>
**何時該重新考慮：** <觸發條件，例如「狀態複雜度超過 X」「需要 time-travel 除錯」>

## 相關

- WBS 任務：<id>（若有）
- 計畫：`plans/<...>.md`（若有）
- 取代：ADR-xxx（若推翻既有決策，**必須**填並說明理由）
```

### 步驟 4：回報

給出檔案路徑，並提示：這份會被 `architect` 與 `planner` 在下次啟動時讀到
（它們的「開始前」步驟會檢查既有 ADR，避免與已定決策衝突）。

## 何時會被自動提起

不用記這個指令，兩個地方會問：

| 時機 | 誰問 |
|---|---|
| `/plan` 的規劃過程做了非顯而易見的技術選型 | planner 完成時提議 |
| 對話中出現「要用哪個 / 選 A 還是 B / 決定用」 | `user-prompt-submit.sh` 關鍵字提示 |

## 使用方式

```
/adr                        # 從當前對話挑決策
/adr 狀態管理選型            # 指定主題
```

## 與其他記錄的分工

| 系統 | 記什麼 |
|---|---|
| **ADR**（本指令） | 為什麼選 A 不選 B——**決策與理由** |
| `/learn` | 可複用的技巧與踩雷模式——**know-how** |
| `/save-session` | 這次做到哪、下次從哪繼續——**進度** |
| `context/<領域>/` | agent 的技術發現報告——**觀察** |
